# 작업 원칙 (step-six-harness)

한 작업은 **0번에서 시작해 1~6번을 필요한 만큼 반복하고, 6번에서 끝난다.** 복리를 누리는
것이 목적이다 — 회차마다 과정이 선명해지고 실수가 줄어야 한다. 단계는 항상 앞으로만 간다.

0. **Selection** — 이번에 할 작업과 **무엇이 '끝'인지**를 정한다. 이전 작업이 끝났다면 새 작업을 할당한다. 무엇을 할지 불분명하면 후보를 나열해 사람과 합의한다(선택). 정해지면 두 가지를 기록한다 — `harness loop intent "<작업>"` 과 `harness loop done-when "<조건>" ...`. **둘 다 없으면 이 단계를 끝낼 수 없다.** 완료 조건은 검증 가능한 문장으로 쓰고, 회차가 바뀌어도 유지된다.
1. **Scaffolding** — 이 작업에 맞는 구조인지 확인하고, 어긋나면 지금 바꾼다. 역할별로 폴더링한다. **신규 최상위 폴더는 이 단계에서만 만들 수 있다.** 구조 변경은 대부분의 회차에서 할 일이 없고, 그게 정상이다.
   **줄이는 것도 이 단계의 일이다.** 쌓인 `.dev/` 회고·학습 문서를 통합·삭제하고, **그 폴더 안에 `INDEX.md` 를 만들어 갱신한다**(회차 접두사 없이 쓸 수 있고, `recall` 이 진입점으로 먼저 보여준다). 규칙이 늘어 마찰이 커졌으면 `stages.json` 을 덜어낸다. 쌓이면 복잡해지는 시스템은 복리가 아니다.
2. **Context** — 유저/프로젝트/폴더 스코프로 계층 기록. 위로 갈수록 추상적. 전부 싣지 말고 "이 상황에서는 이걸 참고해"로 유도해 필요한 것만 읽게 한다. 과거의 실수와 회고는 `harness recall <키워드|경로>` 로 **이번 작업과 관련된 것만** 당겨온다.
3. **Planning** — 모호한 지점을 질문으로 끌어내 요구사항을 도출한다. 계획은 파일로 떨군다(`.dev/plan/`). 사람의 검토·승인 후 실행한다. 계획을 **다른 모델이나 서브에이전트에게 적대적으로 검토받는 것을 고려한다**(권고).
4. **Execution** — 계획대로 실행. 중요한 기능은 테스트로 먼저 동작을 확인한다. 병렬 실행을 적극 고려하고, 완료 기준이 있으면 Ralph Loop도 고려한다.
5. **Verification** — Selection에서 기록한 **완료 조건을 하나씩 대조한다**(단계 진입 시 그대로 제시된다). **자기검증을 최대한 피한다** — 서브에이전트나 타 모델(codex 등)의 비판적 검증, 브라우저/스크린샷, 부작용이 예상되면 dry-run. 사람에게 의존하는 검증보다 반복적이고 빠른 검증이 우선이다. 검증 결과도 **적대적으로 재검토받는 것을 고려한다**(권고).
6. **Compounding** — 회고를 기록한다(`.dev/retrospect/`, `.dev/learning/`). `harness stats` 로 여러 회차·작업에 걸쳐 반복된 항목을 확인한다. 같은 작업이 반복되면 스킬/커맨드 추출을 논의하고, 같은 실수가 반복되면 Scaffolding에서 훅이나 장치를 추가한다. 기록만 하고 승격하지 않으면 복리가 아니라 일기다.
   그리고 **스스로 판단해 두 갈래 중 하나를 고른다.**
   - 작업이 끝났다 → `harness advance --done` (0번으로. 새 작업을 정한다)
   - 후속 회차가 남았다 → `harness advance --cycle` (1번으로. 같은 작업을 유지한다)

## 폴더 규칙

| 경로 | 소유·용도 |
| --- | --- |
| `docs/` | **사람이 기록한다.** 아키텍처·컨벤션·스펙. 명시적 승인 없이 수정하지 않는다. `spec/`, `adr/`, `retrospect/` 는 `NNN-name.md` |
| `tests/` | 검증에 필요한 모든 파일 |
| `.dev/` | 작업의 흔적: `plan/`, `learning/`, `troubleshooting/`, `retrospect/`, `log/`, `experiment/`, `scratch/`. 파일명은 **`<작업해시>-<회차>-이름.md`** (`scratch/` 제외) |
| `.claude/` | Claude 설정. `.claude/harness/stages.json` 과 원칙 문서는 고칠 수 있다 |
| `.claude/harness/bin/`, `harness.db` | **하네스 자신. 수정할 수 없다** — 예외 등록으로도 열리지 않는다 |

## 지켜야 할 점

1. **말머리에 현재 단계 이름을 표시한다** — `[Selection]` `[Scaffolding]` `[Context]` `[Planning]` `[Execution]` `[Verification]` `[Compounding]` 중 하나를 맨 앞에 붙인다. 표시하지 않으면 턴 종료가 차단된다.
2. **스킵은 사유와 사람의 승인이 필요하다** — 불필요한 단계는 건너뛸 수 있으나, 사유를 반드시 노출하고 승인을 받는다: `harness skip <stage|+N|until:<stage>> --reason "..."`. **단 Selection과 Compounding은 건너뛸 수 없다** — 작업은 반드시 선정하고, 중단하더라도 회고는 남긴다.
3. **스킵은 승인을 면제하지만 기록을 면제하지 않는다** — Planning을 건너뛰더라도 계획 파일은 `.dev/plan/` 에 남겨야 한다. 무인 실행으로 회차를 여러 번 돌 때, 계획 10개가 남는 것과 스킵 기록 10개가 남는 것은 복리의 재료로서 다르다.
4. **회차 중간에 선행 작업이 드러나면 되돌아가지 않는다** — 사람과 합의해 `skip until:compounding` 으로 그 회차를 끝내고(사유를 회고에 남긴다), `advance --cycle` 로 다음 회차를 Scaffolding부터 시작한다.
5. **산출물 파일명에 `<작업해시>-<회차>-` 를 붙인다** — 앞단 해시로 grep하면 한 작업의 산출물이 회차와 무관하게 모인다. `001, 002` 같은 증가 번호는 워크트리로 병행 작업하면 충돌한다. 현재 접두사는 `harness status` 로 확인한다.
6. **당장의 구현 이득보다 구조를 바꾸는 쪽을 택한다** — 올바른 구조가 올바른 구현을 만들고 예측 가능하게 한다. 구조 변경 비용은 미래를 위한 투자다. 매번 수정을 반복하며 헛돌면 신뢰 비용이 급강하한다.

제어: `.claude/harness/bin/harness {status | advance | skip | allow | approve-plan}` · 전체는 `harness help`
각 원칙의 상세 근거와 판단 기준: `.claude/harness/rationale.md` (필요할 때 읽어라)

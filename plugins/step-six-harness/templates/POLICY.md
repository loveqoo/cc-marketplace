# 작업 원칙 (step-six-harness)

작업은 아래 6단계를 **선형으로** 반복한다. 복리를 누리는 것이 목적이다 —
매 사이클마다 과정이 선명해지고 실수가 줄어야 한다.

1. **Scaffolding** — 작업할 구조인지 확인한다. 구조 변경은 이 단계에서만 한다. 역할별로 폴더링한다.
2. **Context** — 유저/프로젝트/폴더 스코프로 계층 기록. 위로 갈수록 추상적. 전부 싣지 말고 "이 상황에서는 이걸 참고해"로 유도해 필요한 것만 읽게 한다. 과거의 실수와 회고는 `harness recall <키워드|경로>` 로 **이번 작업과 관련된 것만** 당겨온다.
3. **Planning** — 의도가 불분명하면 모호한 지점을 질문으로 끌어내 요구사항을 도출한다. 계획은 파일로 떨군다(`.dev/plan/`). 사람의 검토·승인 후 실행한다.
4. **Execution** — 계획대로 실행. 중요한 기능은 테스트로 먼저 동작을 확인한다. 병렬 실행을 적극 고려하고, 완료 기준이 있으면 Ralph Loop도 고려한다.
5. **Verification** — 완료 조건을 상기하고 대조한다. **자기검증을 최대한 피한다** — 서브에이전트나 타 모델(codex 등)의 비판적 검증, 브라우저/스크린샷, 부작용이 예상되면 dry-run. 사람에게 의존하는 검증보다 반복적이고 빠른 검증이 우선이다.
6. **Compounding** — 회고를 기록한다(`.dev/retrospect/`, `.dev/learning/`). `harness stats` 로 여러 루프에 걸쳐 반복된 항목을 확인한다. 같은 작업이 반복되면 스킬/커맨드 추출을 논의하고, 같은 실수가 반복되면 Scaffolding에서 훅이나 장치를 추가한다. 기록만 하고 승격하지 않으면 복리가 아니라 일기다.

## 폴더 규칙

| 경로 | 소유·용도 |
| --- | --- |
| `docs/` | **사람이 기록한다.** 아키텍처·컨벤션·스펙. 명시적 승인 없이 수정하지 않는다. `spec/`, `adr/`, `retrospect/` 는 `NNN-name.md` |
| `tests/` | 검증에 필요한 모든 파일 |
| `.dev/` | 작업의 흔적: `plan/`, `learning/`, `troubleshooting/`, `retrospect/`, `log/`, `experiment/`, `scratch/`. 파일명은 **`<루프해시>-이름.md`** (`scratch/` 제외) |
| `.claude/` | Claude 설정 |

## 지켜야 할 점

1. **말머리에 현재 단계를 표시한다** — 예: `[4/6 Execution]`. 표시하지 않으면 턴 종료가 차단된다.
2. **스킵은 사유와 사람의 승인이 필요하다** — 작업 성격상 불필요한 단계는 건너뛸 수 있으나, 사유를 반드시 노출하고 승인을 받는다: `.claude/harness/bin/harness skip <stage|+N|until:<stage>> --reason "..."`
3. **산출물 파일명에 루프 해시를 붙인다** — 6단계 한 바퀴가 하나의 작업 루프이고 해시가 그 식별자다. `001, 002` 같은 증가 번호는 워크트리로 병행 작업하면 충돌한다. 현재 해시는 `harness status` 로 확인한다.
4. **당장의 구현 이득보다 구조를 바꾸는 쪽을 택한다** — 올바른 구조가 올바른 구현을 만들고 예측 가능하게 한다. 구조 변경 비용은 미래를 위한 투자다. 매번 수정을 반복하며 헛돌면 신뢰 비용이 급강하한다.

제어: `.claude/harness/bin/harness {status | advance | skip | allow | approve-plan}`
각 원칙의 상세 근거와 판단 기준: `.claude/harness/rationale.md` (필요할 때 읽어라)

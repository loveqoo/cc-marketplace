# 왜 이렇게 통제하는가

이 문서는 세션 시작에 로드되지 않는다. 하네스가 무언가를 막았을 때, 또는 원칙의 의도를
확인해야 할 때 읽어라. `.claude/harness/POLICY.md` 가 요약, 이 문서가 근거다.

## 통제의 목적: 복리

한 번의 작업을 잘 끝내는 것이 목표가 아니다. **다음 작업이 더 쉬워지는 것**이 목표다.
매번 같은 실수를 반복하며 수정을 되풀이하면 신뢰 비용이 급강하한다. 0~6단계는 그 손실을
막기 위한 장치이고, 마지막이 Compounding인 이유도 그것이다 — 회차가 끝날 때마다
과정이 선명해지고 실수가 줄어야 한다.

그래서 통제가 필요하다. 원칙을 문서로만 두면 압축되거나 잊히고, 급할 때 가장 먼저 무시된다.
훅은 잊지 않는다.

## 단계별 의도

### 0. Selection — 작업의 경계
**이 단계가 작업의 시작점이다.** 이전 작업이 끝났다면 여기서 새 작업을 할당하고, 무엇을 할지
불분명하면 후보를 나열해 사람과 합의한다(선택 과정이다 — 이미 명확하면 건너뛴다).

정해진 작업은 `harness loop intent "<작업>"` 으로 기록한다. 이 기록이 6→2 링크의 시작점이다 —
Context의 `harness recall` 이 인자 없이 호출되면 이 작업에서 키워드를 뽑아 관련된 과거만
찾는다. 작업을 기록하지 않으면 Context가 무엇을 당겨올지 판단할 근거가 없고, 그래서 이 단계는
기록 없이 끝낼 수 없다.

작업 후보를 남겨야 한다면 `.dev/plan/` 에 쓴다. 별도 백로그 저장소를 만들지 않는다 — 기존
구조로 충분하다. **todo-list 를 미리 뽑아 항목마다 회차를 배정하는 식으로 만들지 않았다.**
분해는 "작업의 모양을 시작할 때 이미 안다"를 전제하는데 실제 작업은 대개 그렇지 않고, 그
전제가 틀리면 하네스가 방해물이 된다. 경계만 두고 분해는 사람의 자유에 맡긴다.

### 1. Scaffolding — 구조를 먼저 고친다
구조가 잘못된 채로 구현을 얹으면 매 수정이 우회로를 낳는다. 그래서 구조 변경은 이 단계에
모아 두고, 다른 단계에서는 **신규 최상위 폴더 생성을 차단**한다. 구조를 바꿔야 한다고 느끼면
그건 Scaffolding으로 돌아가라는 신호다. 구조 변경 비용이 큰 것은 정상이며, 미래를 위한
투자로 취급한다.

- `docs/` 는 사람이 기록한다. AI가 스펙과 컨벤션을 자기 편의대로 고치기 시작하면 기준점이
  사라진다. 그래서 쓰기를 막고, 필요하면 사람의 승인을 받게 한다.
- `tests/` 는 검증에 필요한 모든 파일을 모은다.
- `.dev/` 는 작업의 흔적이다. 배운 것(learning), 문제 해결 과정(troubleshooting), 작업 로그,
  디버깅 히스토리, 실험 결과, 스크래치 패드. 이 흔적이 Compounding의 원료다.

**그리고 줄이는 것도 이 단계의 일이다.** Compounding은 관측하고 제안하지만 실제로 무언가를
덜어내는 자리는 여기다 — 문서와 규칙은 구조에 속하기 때문이다.

- `.dev/` 아래 회고·학습 문서가 쌓였으면 통합·삭제하고, 인덱스 문서를 만들어 갱신한다.
  인덱스처럼 특정 회차에 속하지 않는 누적 문서는 `.dev/INDEX.md` 처럼 `.dev/` 직속에 둔다
  (직속 파일은 회차 접두사 규칙을 받지 않는다).
- 규칙이 늘어 마찰이 커졌으면 `stages.json` 을 덜어낸다.

이게 없으면 하네스는 **더하기만 하는 시스템**이 된다. "같은 실수가 반복되면 훅을 추가한다"는
원칙은 규칙을 늘리기만 하고, `.dev/` 는 회차마다 파일이 쌓인다. 50회, 500회를 돌면 마찰이
이득을 넘는다. 쌓이면 복잡해지는 시스템은 복리가 아니다 — 쌓이면서 단순해져야 복리다.

단순화를 별도 단계로 두지 않은 이유는, 단순화가 독립적인 행위가 아니기 때문이다. 무엇을
단순화하는지에 따라 **구조(이 단계)이거나 맥락(Context)** 이다. 별도 단계로 만들면 갈 곳이 없다.

### 2. Context — 한꺼번에 싣지 않는다
컨텍스트는 유한한 자원이다. 하위 스코프가 상위를 덮어쓰는 성질을 이용해 계층적으로 기록하고,
위로 갈수록 추상적으로 유지한다. 유저 영역 → 프로젝트 영역 → 폴더 영역.

핵심은 **"전부 로드"가 아니라 "포인터"** 다. "이런 상황에서는 이걸 참고해"라고 안내해서 필요한
것만 읽게 한다. 이 문서 자체가 그 예다 — POLICY.md는 항상 로드되지만 이 파일은 백틱 경로로만
언급되어 있어 필요할 때만 읽힌다.

### 3. Planning — 모호함을 코드로 옮기지 않는다
의도를 모른 채 실행하면 산출물이 아니라 재작업이 나온다. 모호한 지점은 질문으로 끌어내
요구사항과 태스크로 만든다. 계획은 파일로 남긴다(`.dev/plan/`) — 대화에만 있는 계획은
압축과 함께 사라지고 검토도 불가능하다.

사람의 승인이 필요한 이유는 권위 때문이 아니라 **가장 싼 교정 시점**이기 때문이다. 계획 단계의
오해는 한 문장으로 고쳐지고, 실행 후의 오해는 전체를 되돌린다.

### 4. Execution — 실행 방법 자체를 설계한다
계획을 이해했는지 확인하고 실행한다. 중요한 기능은 테스트로 먼저 동작을 확인한다(그러면
검증이 실행에 내장된다). 실행 방법을 영리하게 고민한다 — 독립적인 작업은 병렬로, 완료 기준이
명확하면 Ralph Loop 같은 반복 구조도 고려한다.

### 5. Verification — 자기검증은 검증이 아니다
자기가 쓴 코드를 자기가 검토하면 같은 사각지대를 반복한다. 그래서 외부 시선을 요구한다:
서브에이전트, 다른 기업의 모델(codex, copilot 등)의 비판적 검증, 브라우저 제어나 MCP로 실제
화면 확인, 스크린샷, 부작용이 예상되면 dry-run.

사람에게 의존하는 검증은 되도록 피한다 — 느리고 병목이 된다. **반복적이고 빠른 검증이 우선**이다.
컨텍스트에 이미 있는 검증 수단을 먼저 찾아보고, 적절하면 도입한다.

하네스는 이 단계에서 증거 없이 턴을 끝내지 못하게 막는다. 증거로 인정하는 것: 테스트/린트/타입체크
명령 실행, 서브에이전트 호출, 브라우저 계열 MCP 도구 사용, `--dry-run` 실행.

### 6. Compounding — 흔적을 자산으로 바꾼다
무엇이 잘못됐고 무엇을 배웠는지 기록한다. 그리고 한 단계 더 나아간다:

- 같은 **작업**이 반복되면 → 스킬이나 커맨드로 추출하는 것을 논의한다.
- 같은 **실수**가 반복되면 → Scaffolding 단계에서 훅이나 다른 장치를 고려한다.

기록만 하고 승격하지 않으면 복리가 아니라 일기다.

그리고 이 단계에서 **작업이 끝났는지 스스로 판단한다.** 두 갈래가 있다.

| 판단 | 명령 | 결과 |
| --- | --- | --- |
| 작업이 끝났다 | `advance --done` | 작업을 닫고 0번으로. 새 작업을 정한다 |
| 후속 회차가 남았다 | `advance --cycle` | 1번으로. **같은 작업을 유지하고 회차만 올린다** |

이 갈래가 "한 작업이 여러 회차에 걸친다"를 표현한다. 하네스는 어느 쪽인지 판정하지 않는다 —
작업이 끝났는지는 사람과 모델만 안다. 그래서 게이트가 아니고, 맨손 `advance` 는 두 선택지를
보여주고 멈춘다.

회차가 바뀌면 계획·검증 증거가 초기화된다. 초기화하지 않으면 2회차 Planning 이 1회차
계획서로 통과한다. 작업 선정 기록(`intent_set`)만 남는다 — 작업은 그대로이므로 다시 정할
필요가 없다. 이전 회차의 계획·회고 **파일은 그대로 남고**, 파일명의 회차로 구분된다.

## 상태와 시퀀스: 왜 해시이고, 왜 DB를 커밋하지 않는가

한 작업이 `260804-a3f9c1` 같은 해시로 식별되고, 1~6단계를 여러 회차 돌 수 있다.
이 해시가 `.dev/` 산출물 파일명의 접두사가 된다.

`001, 002` 처럼 증가하는 번호를 쓰지 않는 이유는 **다음 번호를 알려면 다른 워크트리의
상태를 읽어야 하기 때문**이다. 병행 작업 중인 두 워크트리는 서로를 볼 수 없으니 둘 다
`003` 을 만들고 머지 시점에 충돌한다. 해시는 조정이 필요 없다.

상태는 `.claude/harness/harness.db` (SQLite)가 갖는다. 이 DB의 역할은 딱 두 가지다 —
**해시 발급과 현재 상태 제어.** 작업이 닫히면 그 작업의 행은 버린다. 영구 기록은 각 폴더에
남은 파일이고, 파일명이 해시를 갖고 있으니 그게 시퀀스이자 인덱스다.

그래서 DB는 커밋하지 않는다(gitignore). 얻는 것:

- 워크트리마다 자기 단계를 독립적으로 갖는다. 다른 브랜치의 "현재 단계"가 머지로 흘러들어오지 않는다.
- 바이너리 파일이 git 히스토리를 불리지 않는다. 머지 충돌도 원리적으로 없다.
- 지워도 된다. `harness status` 가 새 작업을 만들고, 기존 해시로 되돌아가려면
  `harness loop adopt <해시>` 를 쓴다.
- 병렬 툴 호출로 훅이 동시에 발화해도 트랜잭션이 쓰기를 직렬화한다. 단일 JSON 파일이었다면
  read-modify-write 경합으로 증거가 유실됐다.

**한 가지 대가**: 스킵된 단계는 파일을 남기지 않으므로, 작업이 닫히면 "무엇을 왜 건너뛰었나"만
사라진다. 그래서 Compounding 진입 시 하네스가 스킵 기록을 노출한다 — 회고 md 로
옮겨 적으면 그 사실이 git 에 남는다. 회고는 원래 그걸 적는 자리다.

## 엔진은 프로젝트 안에 두고, 하네스 자신은 잠근다

`init` 이 엔진 사본을 `.claude/harness/bin/harness.py` 에 두고 래퍼가 그것을 실행한다.
사본은 gitignore 되고 세션 시작마다 갱신되므로 플러그인 버전과 어긋나지 않는다.

**왜 사본을 두는가.** 모델이 실행하는 명령이 작업 디렉터리 밖의 파일을 가리키면 막힌다 —
auto-mode 안전성 분류기와 샌드박스가 각각 한 번씩 실제로 막았다. 두 번 모두 같은 원인이었다.
훅은 Bash 툴을 거치지 않으므로 영향이 없었고(플러그인 캐시에서 그대로 실행된다), 막힌 것은
모델이 치는 CLI 뿐이었다.

**그래서 잠금이 필요해진다.** 사본이 프로젝트 안으로 들어오면 `.claude/**` 는 `context`
클래스라 여러 단계에서 쓰기가 열린다. 즉 모델이 자기를 통제하는 엔진을 고쳐 게이트를
무력화할 수 있다. `folder_rules.protected_paths` 가 이것을 막는다:

| 경로 | 이유 |
| --- | --- |
| `.claude/harness/bin/**` | 엔진·래퍼를 고치면 게이트가 무력화된다 |
| `.claude/harness/harness.db` | 덮어쓰면 DB 가 손상되고, 손상 시 차단하지 않는 설계(세션을 벽돌로 만들지 않기 위한 것) 때문에 **게이트 전체가 조용히 꺼진다** |

이 차단은 `allow` 로도 열리지 않는다. 예외를 허용하면 잠금의 의미가 없다.

규칙 자체는 여전히 고칠 수 있다 — `stages.json` 과 원칙 문서는 열려 있다. **무엇을 강제할지는
바꿀 수 있고, 강제하는 장치는 못 바꾼다.** 이 구분이 잠금의 요점이다.

## 복리를 만드는 것: 관측 기록과 pull 조회

복리가 되려면 Compounding이 남긴 것을 다음 회차·작업의 Context가 읽어야 한다. 그 링크를
잇는 것이 `event` 테이블이다.

**모델의 자기신고를 쓰지 않는다.** 자기신고는 부정확하고 조작 가능하다. 훅은 이미 사실을
관측하고 있으니 판정에만 쓰고 버리지 말고 적립한다.

| 기록되는 것 | 무엇을 말해주나 |
| --- | --- |
| `block` (규칙별 차단) | 어떤 규칙에 반복적으로 걸리는가 → 규칙이 틀렸거나 습관이 틀렸다 |
| `skip` (단계별 스킵) | 늘 건너뛰는 단계 → 그 단계 정의가 이 프로젝트에 안 맞다 |
| `stop_gate` / `bypass` | 검증·회고를 습관적으로 빠뜨리는가 / 게이트를 얼마나 뚫는가 |
| `tool_fail` | 같은 명령이 같은 이유로 반복 실패 → "동일한 실수"의 가장 직접적 증거 |
| `edit` | 한 작업에서 같은 파일을 몇 번 고쳤는가 → 구조 냄새 |

작업이 닫혀도 `event` 와 작업 인덱스(해시·의도·기간)는 남는다. 버리는 것은 진행 중 상태
(`stage`, `evidence`, `wgrant`)뿐이다. event 를 버리면 복리의 원료가 사라진다.

### Context 는 밀지 않고 당긴다

Context 진입 시 상위 반복 항목을 자동으로 주입하는 것은 **이 문서의 Context 원칙을 위반한다** —
"전부 싣지 말고 필요한 것만 읽게 한다"인데, 무관한 과거 실수까지 컨텍스트를 먹기 때문이다.
이전 작업의 실수가 지금 작업과 무관하면 읽지 않아도 된다.

그래서 하네스는 **조회 인터페이스만** 제공한다. 무엇이 관련 있는지는 Selection에서 정한
task 를 근거로 모델이 판단한다.

```sh
harness recall <키워드|경로>   # 관련된 것만 당겨온다
harness stats                  # 전체 그림이 필요할 때
```

이벤트 조회는 정확하게(세는 것이므로), 회고 파일 검색은 넓게(읽을 후보를 고르는 것이므로)
매칭한다 — `src/api.ts` 로 조회하면 이벤트는 그 경로만, 파일은 `api` 를 다룬 산문까지 걸린다.

Compounding은 반대다. 막 끝낸 회차 자신의 기록은 무조건 관련 있으니 단계 진입 시 밀어준다.

### 무엇을 강제하지 않기로 했는가

아래는 구현이 빠진 것이 아니라 **넣지 않기로 결정한 것**이다. 완벽한 통제가 목표가 아니다 —
과잉 통제는 마찰만 늘리고, 마찰이 커지면 게이트를 끄게 되고, 그러면 하네스가 사라진다.

| 강제하지 않는 것 | 이유 |
| --- | --- |
| 계획의 **내용** 검사 | 좋은 계획인지는 판단이다. 파일 존재와 사람의 승인까지가 훅의 한계 |
| **무엇을** 검증했는지 검사 | 검증 수단 선택은 판단이다. 증거의 존재까지만 본다 |
| 승격의 **내용** 검사 | 무엇으로 승격할지, 실제로 훅을 고쳤는지는 판단이다. 결정을 요구하는 것까지가 훅의 한계 |
| 정리(`tidy`)의 실행 | 후보만 제시한다. 무엇을 지우고 무엇을 남길지는 판단이다 |
| **셸 간접 호출 차단** | 아래 "막지 못하는 것" 참고 — 원리적으로 닫을 수 없다 |
| **턴 종료의 무한 차단** | 상한이 있다. 아래 "차단 상한" 참고 |

### 막지 못하는 것: 셸 간접 호출

동의가 필요한 명령의 탐지는 `PreToolUse` 가 받은 **Bash 명령 문자열**에 대한 정규식이다.
따라서 경로를 변수에 넣어 호출하면 탐지를 피한다.

```sh
X=.claude/harness/bin/harness; "$X" skip verification --reason x   # 탐지되지 않는다
```

이건 고칠 수 없다. 문자열을 아무리 정교하게 봐도 셸의 표현력을 따라갈 수 없고, 실제 실행
프로그램을 알려면 훅이 프로세스 실행을 가로채야 하는데 `PreToolUse` 는 그 층이 아니다.

**다만 "간접 호출은 못 막는다"가 "직접 형태를 대충 본다"의 변명이 되지는 않는다.** 두 번째
적대적 리뷰에서 직접 형태 여섯 가지가 뚫려 있었다 — `find … -delete`, `find … -exec rm`,
`dd of=<경로>`, `printf >|<경로>`, `rm -rf` 로 상위 디렉터리 통째, 그리고 `loop new` 의
동의 게이트를 옵션 위치(`loop --reason=x new`)나 앞선 무해한 명령(`status; loop new`)으로
지나치는 것. 전부 변수 없이 경로를 그대로 쓴 형태라 막을 수 있었고, 막았다. 경계는
"셸 트릭"이 아니라 **"경로가 문자열에 그대로 보이는가"** 다.

그래서 이 하네스는 **적대적인 모델을 막는 장치가 아니다.** 규칙을 지키려는 모델이 실수로
어긋나는 것을 잡고, 어긋난 사실을 기록에 남기는 장치다. 우회는 막지 못하지만 우회 시도는
`block` 이벤트(`no_reason`, `bypass_mode`, `protected_bash`)로 남고 `stats` 에 드러난다 —
그것이 이 층에서 할 수 있는 전부다.

같은 이유로 이 우회 기록들은 **승격 후보에서 제외한다**(`promotion.exclude_rules`). 기계화할
습관이 아니라 규율 신호이고, 승격 절차에 넣으면 사용자가 봐야 할 사실이 결정으로 세탁된다.

### 턴 이어붙임: 무인 실행의 유일한 추진 장치

하네스는 원래 **반응만 하고 턴을 시작하지 않는다.** 훅은 도구 호출이나 턴 종료에 붙는 것이지
스스로 일을 시작할 수 없다. `Stop` 훅으로 턴 종료를 막으면 그 한계를 밀 수 있다 — 종료 조건을
다 채웠는데 단계가 남았으면 "멈추지 말고 이어서 진행하라"고 되돌린다.

**이걸 켤 수 있게 만든 조건이 진전 감지다.** 없이 켰을 때 첫 실험에서 모델이 불가능한 명령을
4회 반복하며 헛돌았다. 그래서 이어붙일 때마다 지문을 남긴다.

```
지문 = (현재 단계, evidence 수, 모델 활동 이벤트 수)
연속 2회 지문이 그대로면 → 이어붙이기를 멈추고 사람에게 물으라고 한다
```

지문에서 **하네스 자신이 남기는 기록은 뺀다**(`stop_continue`, `stop_gate`, `bypass`,
`cycle_close`). 빼지 않으면 이어붙임 이벤트가 이벤트 수를 늘려 지문이 매번 바뀌고, 진전
감지가 자기 자신을 진전으로 세면서 영원히 발동하지 않는다 — 실제로 그렇게 만들어서 5회
헛돌았고, 수동 실행에서 눈으로 보고 찾았다(테스트 313개는 이 경로를 덮지 않았다).

읽기만 한 턴은 지문이 그대로다. 그건 의도한 것이다 — 단계 종료 조건은 증거·모델 활동·단계
전이로만 채워지므로, 그 셋이 그대로면 종료에 가까워지지 않았다.

진전 감지가 있으니 **상한을 넉넉히 줄 수 있다**(기본 6회). 일이 실제로 진행되는 동안은 여섯
번 밀어주고, 헛도는 경우는 두 번에서 끊는다. 멈춘 사실은 `stop_stalled` 이벤트로 남아
`stats` 에 드러난다.

### 차단 상한: 왜 무한히 막지 않는가

`Stop` 훅의 조건별 차단 횟수에는 상한이 있다(`stop_block_limits`, 승격은 2회). 상한을 넘으면
미충족 상태로 턴 종료를 허용하고 `bypass` 이벤트와 `systemMessage` 를 남긴다.

무한히 막으면 세션이 벽돌이 된다 — 조건을 충족할 방법이 없는 상황(예: 필요한 도구가 없다)에
빠지면 영원히 끝나지 않는다. 그래서 **턴 종료는 결국 열리지만 단계는 열리지 않는다.**
`advance` 는 계속 거부하므로 작업이 다음 단계로 가지는 못한다. 즉 상한은 "탈출구"가 아니라
"숨 쉴 틈"이다.
| 병렬 실행·Ralph Loop 강제 | 실행 전략은 판단이다 |
| Bash 완전 차단 | 오탐으로 정상 작업을 망치는 쪽이 더 해롭다. `python -c` 등은 통과한다 |

훅 · 스킵 제한 · 말머리 규칙이면 충분하다. 나머지는 원칙 문서와 사람의 판단에 맡긴다.

### 측정할 수 있는 것과 없는 것

수치는 **과정**을 측정한다 — 차단, 스킵, 실패, 재편집. **품질**은 측정하지 못한다.
"이 규칙에 12번 걸렸다"는 말할 수 있지만 "설계가 나빴다"는 말할 수 없다. 그건 회고 텍스트와
사람의 판단 영역이다.

## 왜 승격을 강제하는가 (기록 → 자산)

기록만 쌓는 시스템은 복리가 아니다. 이건 우리 의견이 아니라 관측된 결과다.

AGENTS.md·CLAUDE.md 를 가진 오픈소스 레포 100개를 조사한 연구에서 가장 흔한 설정 냄새는
**lint leakage 가 62%** 였다 — *린터나 훅으로 막을 수 있는 것을 산문으로 적어둔 것*. 두 번째는
context bloat 42%(216~1477줄까지 부풀었고, 커지면 초반 지시가 묻혀 무시된다). 흔한 악순환은
이렇다: 실수 → 규칙 한 줄 추가 → 잠시 나아짐 → 또 다른 실수 → 또 한 줄. 파일이 터진다.

우리는 이 냄새를 원리적으로 피할 수 있는 위치에 있다. **하네스 자신이 훅이기 때문이다.**
반복되는 실수를 산문이 아니라 기계로 옮길 수 있다. 그러려면 반복을 세는 데서 멈추면 안 된다.

### 세 가지 장치와 그 근거

| 장치 | 무엇을 하는가 | 어디서 온 발상인가 |
| --- | --- | --- |
| **실패 지점 주입** | 같은 도구 실패가 2번째면 그 자리에서 반복 횟수·이전 오류·관련 회고 파일을 알려준다 | CODESKILL 의 event-driven 회수 — 에러 메시지를 키로 **온라인** 회수하는 것이 작업 시작에 한 번 밀어넣는 것보다 효과가 컸다. 실패한 순간은 무엇을 물어볼지 이미 아는 유일한 순간이다 |
| **승격 결정 강제** | 여러 작업에서 반복된 항목은 Compounding 의 종료 조건이다. 승격하거나 사유와 함께 보류해야 끝난다 | ExpeL 의 중요도 투표(0이 되면 삭제), cass 의 성숙도(`candidate→established→proven`) |
| **예산과 정리** | `LEARNED.md` 는 줄 수 상한이 있고, `tidy` 가 삭제·병합 후보를 제시한다 | CODESKILL 의 skill bank 는 add/merge/**drop** 으로 **크기가 수렴**한다. 무한히 자라는 저장소는 실패한 저장소다 |

### 보류를 왜 승인 없이 허용하는가

`promote --decline` 은 사용자 다이얼로그를 띄우지 않는다. 게이트 우회가 아니라 **기록**이기
때문이다. 그러면 모델이 전부 보류하고 빠져나갈 수 있는 것 아닌가 — 맞다. 그래서 두 가지를 둔다.

1. **보류는 event 로 남는다.** `stats` 에 "승격 보류"로 드러나고 사용자가 본다.
2. **보류는 되돌아온다.** 보류한 항목이 이후 2개 작업에서 다시 걸리면 결정이 무효화되고
   (`regressed`) 목록에 다시 올라온다. 승격했는데 재발한 경우도 같다 — **그 승격이 통하지
   않았다는 객관적 증거**이기 때문이다.

여기서 다이얼로그를 요구하면 무인 실행이 회차마다 멈춘다. 승인은 면제하고 기록은 면제하지
않는 것이 이 하네스의 일관된 선택이다(스킵도 같다).

### 시각 비교는 문자열이 아니라 절대 시각으로 한다

`at`, `recheck_at` 은 `2026-08-04T12:00:00+0900` 형태로 저장된다. 이걸 SQL `>` 로 비교하면
오프셋이 섞이거나 DST 전환이 있을 때 사전순과 실제 순서가 어긋난다 —
`2026-11-01T01:30:00-0500` 은 `2026-11-01T01:45:00-0400` 보다 **실제로는 나중인데** 문자열로는
작다. 워크트리를 다른 타임존 장비에서 열면 그대로 걸린다. 그래서 비교는 Python 에서 epoch 로
바꿔서 한다(`ts_epoch`). 한 항목의 이벤트 수는 작으므로 행을 가져와도 싸다.

재발 판정의 경계는 결정 시각 **+1초**다. 초 단위 정밀도라서 `>` 로 두면 같은 초의 이벤트를
영구히 놓치고, `>=` 로 두면 결정 직전의 이벤트가 결정을 즉시 무효화한다.

### 게이트는 저장된 성숙도를 믿지 않는다

`promotion.maturity` 는 표시용 캐시다. 게이트(`criterion_met`)와 `LEARNED.md` 생성은
**그 자리에서 다시 계산한다**(`is_regressed`). 저장값만 보면 `stats`/`tidy`/`promote` 를
아무도 실행하지 않은 세션에서 재발한 항목이 `established` 로 남아 Compounding 을 통과한다 —
실제로 그렇게 새어나갔고, 그게 이 기능의 핵심 절반이었다.

### 성숙도를 왜 결정론적으로 계산하는가

`established → proven` 은 "승격 후 재발 없이 작업 N개가 지났다"로만 판정한다. LLM 에게
"이 규칙이 좋은가"를 묻지 않는다. cass 가 큐레이션 단계에 의도적으로 LLM 을 넣지 않은 이유가
같다 — LLM 이 자기 판단을 다시 판단하면 등급이 표류하고(context collapse) 근거 없는 확신이
쌓인다. 우리에게는 이미 객관 신호가 있다: **같은 이벤트가 또 걸리는가.**

### 복리를 어떻게 측정하는가 (그리고 무엇을 측정할 수 없는가)

`harness metrics` 다. 세 블록이고 **점수가 없다.**

**① 승격 생존율이 유일하게 엄밀한 측정이다.** "하네스 있기 전/후"는 비교할 수 없다 — 기준선이
없다. 하지만 **"이 규칙을 승격한 전/후"는 비교할 수 있다.** 각 승격은 개입 시점과 대상과
결과(그 뒤 또 걸리는가)를 모두 갖춘 하나의 실험이다. 종류별 재발률이 쌓이면 62% lint leakage
가설을 이 프로젝트 안에서 직접 검증하게 된다 — 훅으로 옮긴 것은 정말 안 걸리는가, 산문으로
적어둔 것은 정말 다시 걸리는가.

여기에 **주장 대비 사실**을 붙인다. `--as hook` 은 주장이다. 그래서 승격할 때 그 회차에 맞는
파일 변경이 실제로 있었는지 관측해 기록한다(`promote_verify`). 막지는 않는다 — 무엇을 어떻게
고칠지는 판단이다. 하지만 `변경관측 2/3` 이 나오면 세 건 중 한 건은 말만 한 것이다.

**② 마찰 지표는 교란된다.** 차단·반복실패·재편집은 이미 기록되지만 **작업 난이도를 통제할
방법이 없다.** "5회차가 1회차보다 차단이 적다"는 규칙이 좋아진 결과일 수도, 쉬운 작업이었을
수도 있다. 그래서 개별 비교가 아니라 구간 추세로만 읽고, 그마저 정황 증거다.

**③ 점수를 만들지 않는 이유가 이 설계의 핵심이다.** 차단 횟수를 목표로 삼으면 차단을 피하는
법을 배운다 — 아무것도 시도하지 않거나 `skip`·`bypass`·`--decline` 으로 빠져나가면 차단은
줄어든다. 마찰이 준 게 아니라 회피가 는 것인데 숫자는 똑같이 예뻐진다. 우리 하네스에는 그
탈출구가 다 있다. 그래서 마찰 지표와 **회피 지표를 반드시 같은 화면에 놓는다.**

| 관측 | 해석 |
| --- | --- |
| 마찰 ↓ · 우회 → | 개선 신호 |
| 마찰 ↓ · 우회 ↑ | **회피**. 게이트가 연극이 되고 있다 |
| 마찰 → · 우회 ↑ | 규칙이 이 프로젝트에 맞지 않는다 |

`metrics` 가 이 판정을 자동으로 붙인다. 지표를 하나로 합치면 이 구분이 사라진다.

**측정하지 못하는 것**: 결과물의 품질, 그 회차가 필요했는지(끈질김인지 헛돎인지), 사람이 아낀
시간, 회고 텍스트의 가치. 즉 측정하는 것은 **마찰**이고 알고 싶은 것은 **가치**다. 마찰은
대리 지표일 뿐이며, 그 사실을 출력 맨 아래에 매번 적는다.

**표본 이야기**: 승격 종류별 재발률에 의미를 붙이려면 20~30건이 필요하고, `min_loops: 3` 이니
작업 수십 개를 돈 뒤다. 지금 만드는 이유는 데이터가 시간에만 쌓이기 때문이고, 동시에 답은
한참 뒤에 온다는 뜻이다. 표본이 20건 미만이면 `metrics` 가 비율을 믿지 말라고 경고한다.

### 왜 회차 경계에서 스냅샷을 남기는가

`close_loop` 이 `stage` 행을 지우므로 작업이 닫히면 회차별 비용을 되살릴 수 없다. 그래서
회차 경계(`advance --cycle`/`--done`)에서 그 회차의 집계를 `cycle_close` 이벤트 한 줄로
남긴다. `event` 는 작업이 닫혀도 살아남으므로 측정이 나중에 가능해진다.

스키마는 바꾸지 않았다 — 측정도 승격 검증도 **새 event 종류로만** 기록한다. 열을 추가하면
구버전 DB 에서 `no such column` 으로 하네스가 죽고, 마이그레이션은 하지 않기로 했다.

### `LEARNED.md` 가 `POLICY.md` 와 분리된 이유

둘 다 CLAUDE.md 앵커로 항상 로드되지만 소유자가 다르다. `POLICY.md` 는 사람이 정한 원칙이고,
`LEARNED.md` 는 하네스가 `promotion` 테이블에서 **생성한다**. 섞으면 손으로 쓴 것과 생성된
것이 구분되지 않아 어느 쪽도 안전하게 고칠 수 없다. 그래서 `LEARNED.md` 는 쓰기 금지 경로다.

## 스킵 자동 승인: 왜 켜는 것만 승인이 필요한가

`harness auto-skip on` 은 스킵의 동의 다이얼로그를 끈다. 급한 기간에 게이트가 방해가 될 때
쓰는 장치다. 비대칭이 하나 있다:

- **켜기는 사용자 승인이 필요하다.** 게이트 자체를 무력화하는 행위이므로, 이것까지 자유롭게
  허용하면 모델이 스스로 켜서 모든 스킵을 통과할 수 있다. 그러면 하네스가 아니다.
- **끄기는 승인이 필요 없다.** 게이트를 복원하는 방향이라 언제든 안전하다.

켜져 있어도 없어지는 것은 **다이얼로그뿐**이다. `--reason` 은 여전히 필수이고, 기록에는
`authorized_by=auto` 로 남아 사람이 승인한 스킵과 구분된다. 스킵이 자동 승인될 때마다
`systemMessage` 로 사용자에게 노출되고, `status` 와 세션 시작 컨텍스트에 `⚠ ON` 이 계속
표시된다 — 켜둔 사실을 잊는 것이 가장 위험하다.

**범위를 좁혀라.** `--uses N` 은 N회 후, `--scope loop` 는 작업이 바뀌면 자동 만료된다.
무제한으로 켜두는 것이 가장 위험한데, 게이트가 열린 것을 잊기 때문이다. 만료되면 `status` 가
이유까지 알려준다 — 사용자가 왜 게이트가 돌아왔는지 모르면 안 된다.

만료 판정은 플래그를 뒤집지 않고 계산으로 한다. 플래그(`auto_skip`)는 사용자의 **의도**를
담고, 실효 상태는 범위·횟수를 함께 보고 결정한다. 소진 시점에 플래그를 `off` 로 덮어쓰면
"왜 꺼졌는지"를 잃는다.

스킵이 자꾸 막혀 불편하다면 자동 승인을 켜기 전에 `stages.json` 이 이 프로젝트에 맞는지
검토하는 게 낫다. 게이트를 끄는 것보다 규칙을 고치는 것이 옳은 해결이고, 그게 Compounding
단계에서 할 일이다.

### 스킵은 승인을 면제하지만 기록을 면제하지 않는다

이게 무인 실행이 성립하는 조건이다. `stages.json` 의 `skip_requires` 에 걸린 조건은 스킵으로도
면제되지 않는다 — Planning 은 `plan_file` 이 걸려 있어서, 건너뛰더라도 계획 파일은 남아야 한다.

무인으로 회차를 열 번 돌았을 때 **계획 열 개가 남는 것과 스킵 기록 열 개가 남는 것은 복리의
재료로서 다르다.** 전자는 다음 회차의 Context 가 `recall` 로 당겨올 수 있고 Compounding 이
패턴을 볼 수 있다. 후자는 "건너뛰었다"만 남는다.

회고도 같은 원칙이다. Compounding 은 `skippable: false` 이고 `retro_file` 이 종료 조건이므로,
자동 승인이 켜져 있어도 회고 없이 그 단계를 벗어날 방법이 없다 — 건너뛰기도, 작업 종료도,
다음 회차로 넘어가기도 전부 막힌다.

정리하면 무인 실행은 **사람의 승인을 생략하는 것이지 기록을 생략하는 것이 아니다.** 사람의
결정은 Selection 에서 목표와 완료 조건으로 한 번 내려지고, 그 뒤로는 하네스가 기록을 강제하며
회차를 돈다.

## 하네스가 강제하는 것과 하지 않는 것

훅은 확정적인 사실만 판정할 수 있다. 그래서 역할을 나눈다.

**훅이 강제한다 (기계적으로 판정 가능)**

| 규칙 | 방식 |
| --- | --- |
| `docs/` 쓰기 | 차단 — 승인 시 예외 |
| 단계별 쓰기 허용 경로 | 차단 |
| 신규 최상위 폴더 | Scaffolding 외 차단 |
| `.dev/` 하위 폴더명, `docs/**/NNN-name.md` | 차단 |
| `.dev/` 파일명에 `<작업해시>-<회차>-` 접두사 없음 | 차단 |
| 계획 파일 + 사람의 승인 없이 Planning 종료 | `advance` 거부 |
| 검증 증거 없이 Verification 종료 | 턴 종료 차단 |
| 회고 기록 없이 Compounding 종료 | 턴 종료 차단 |
| 사유 없는 스킵 | 차단 · 사유 있으면 사용자 승인 다이얼로그 |
| 말머리에 단계 미표시 | 턴 종료 차단 |

턴 종료 차단에는 상한이 있다(`stages.json` 의 `stop_block_limits`). 무한 루프를 막기 위한
것이고, 상한을 소진해 통과할 때는 **`systemMessage` 로 사용자에게 그 사실을 노출한다** —
조용한 우회가 없는 게 상한을 없애는 것보다 중요하다.

**훅이 판정하지 않는다 (판단 영역)**

계층적 컨텍스트를 잘 짰는지, 병렬 실행이나 Ralph Loop이 적절한지, 검증 수단 선택이 타당한지,
스킵 사유가 합리적인지, 구조 변경이 지금 옳은지. 훅은 "합리적인 이유"를 판정할 수 없다.
그래서 사유의 **기록**만 강제하고, 판정은 사람에게 넘긴다. 이게 훅으로 가능한 최대치이고
동시에 감사 가능한 형태다.

## 막혔을 때

```sh
.claude/harness/bin/harness status                              # 현재 단계·종료 조건·증거
.claude/harness/bin/harness advance                             # 다음 단계 (조건 미충족이면 거부)
.claude/harness/bin/harness advance --done                      # (Compounding) 작업 종료 → Selection
.claude/harness/bin/harness advance --cycle                     # (Compounding) 다음 회차 → Scaffolding
.claude/harness/bin/harness skip <stage|+N|until:<stage>> --reason "..."   # 사용자 승인 필요
.claude/harness/bin/harness allow "docs/spec/003-x.md" --reason "..."      # 쓰기 예외, 사용자 승인 필요
.claude/harness/bin/harness approve-plan .dev/plan/<해시>-x.md   # 계획 승인 기록
.claude/harness/bin/harness loop                                 # 현재 작업 해시·브랜치
.claude/harness/bin/harness loop new --intent "..."              # 작업을 닫고 새로 시작
.claude/harness/bin/harness loop adopt <해시> --reason "..."      # 기존 해시로 재연결
```

차단은 하네스가 틀렸다는 신호일 수도 있다. 규칙 자체가 작업을 방해한다면 그것을 Compounding에서
논의하라 — `stages.json` 이 규칙의 단일 출처이고 수정 가능하다.

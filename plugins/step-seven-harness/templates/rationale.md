# 왜 이렇게 통제하는가

이 문서는 세션 시작에 로드되지 않는다. 하네스가 무언가를 막았을 때, 또는 원칙의 의도를
확인해야 할 때 읽어라. `.claude/harness/POLICY.md` 가 요약, 이 문서가 근거다.

## 통제의 목적: 복리

한 번의 작업을 잘 끝내는 것이 목표가 아니다. **다음 작업이 더 쉬워지는 것**이 목표다.
매번 같은 실수를 반복하며 수정을 되풀이하면 신뢰 비용이 급강하한다. 0~6단계는 그 손실을
막기 위한 장치이고, 마지막이 Compounding인 이유도 그것이다 — 회차가 끝날 때마다
과정이 선명해지고 실수가 줄어야 한다.

그래서 통제가 필요하다. 원칙을 문서로만 두면 압축되거나 잊히고, 급할 때 가장 먼저 무시된다.
훅은 잊지 않는다.

## 단계별 의도

### 0. Selection — 작업의 경계
**이 단계가 작업의 시작점이다.** 이전 작업이 끝났다면 여기서 새 작업을 할당하고, 무엇을 할지
불분명하면 후보를 나열해 사람과 합의한다(선택 과정이다 — 이미 명확하면 건너뛴다).

정해진 작업은 `harness loop intent "<작업>"` 으로 기록한다. 이 기록이 6→2 링크의 시작점이다 —
Context의 `harness recall` 이 인자 없이 호출되면 이 작업에서 키워드를 뽑아 관련된 과거만
찾는다. 작업을 기록하지 않으면 Context가 무엇을 당겨올지 판단할 근거가 없고, 그래서 이 단계는
기록 없이 끝낼 수 없다.

작업 후보를 남겨야 한다면 `.dev/plan/` 에 쓴다. 별도 백로그 저장소를 만들지 않는다 — 기존
구조로 충분하다. **todo-list 를 미리 뽑아 항목마다 회차를 배정하는 식으로 만들지 않았다.**
분해는 "작업의 모양을 시작할 때 이미 안다"를 전제하는데 실제 작업은 대개 그렇지 않고, 그
전제가 틀리면 하네스가 방해물이 된다. 경계만 두고 분해는 사람의 자유에 맡긴다.

### 1. Scaffolding — 구조를 먼저 고친다
구조가 잘못된 채로 구현을 얹으면 매 수정이 우회로를 낳는다. 그래서 구조 변경은 이 단계에
모아 두고, 다른 단계에서는 **신규 최상위 폴더 생성을 차단**한다. 구조를 바꿔야 한다고 느끼면
그건 Scaffolding으로 돌아가라는 신호다. 구조 변경 비용이 큰 것은 정상이며, 미래를 위한
투자로 취급한다.

- `docs/` 는 사람이 기록한다. AI가 스펙과 컨벤션을 자기 편의대로 고치기 시작하면 기준점이
  사라진다. 그래서 쓰기를 막고, 필요하면 사람의 승인을 받게 한다.
- `tests/` 는 검증에 필요한 모든 파일을 모은다.
- `.dev/` 는 작업의 흔적이다. 배운 것(learning), 문제 해결 과정(troubleshooting), 작업 로그,
  디버깅 히스토리, 실험 결과, 스크래치 패드. 이 흔적이 Compounding의 원료다.

**그리고 줄이는 것도 이 단계의 일이다.** Compounding은 관측하고 제안하지만 실제로 무언가를
덜어내는 자리는 여기다 — 문서와 규칙은 구조에 속하기 때문이다.

- `.dev/` 아래 회고·학습 문서가 쌓였으면 통합·삭제하고, 인덱스 문서를 만들어 갱신한다.
  인덱스처럼 특정 회차에 속하지 않는 누적 문서는 `.dev/INDEX.md` 처럼 `.dev/` 직속에 둔다
  (직속 파일은 회차 접두사 규칙을 받지 않는다).
- 규칙이 늘어 마찰이 커졌으면 `stages.json` 을 덜어낸다.

이게 없으면 하네스는 **더하기만 하는 시스템**이 된다. "같은 실수가 반복되면 훅을 추가한다"는
원칙은 규칙을 늘리기만 하고, `.dev/` 는 회차마다 파일이 쌓인다. 50회, 500회를 돌면 마찰이
이득을 넘는다. 쌓이면 복잡해지는 시스템은 복리가 아니다 — 쌓이면서 단순해져야 복리다.

단순화를 별도 단계로 두지 않은 이유는, 단순화가 독립적인 행위가 아니기 때문이다. 무엇을
단순화하는지에 따라 **구조(이 단계)이거나 맥락(Context)** 이다. 별도 단계로 만들면 갈 곳이 없다.

### 2. Context — 한꺼번에 싣지 않는다
컨텍스트는 유한한 자원이다. 하위 스코프가 상위를 덮어쓰는 성질을 이용해 계층적으로 기록하고,
위로 갈수록 추상적으로 유지한다. 유저 영역 → 프로젝트 영역 → 폴더 영역.

핵심은 **"전부 로드"가 아니라 "포인터"** 다. "이런 상황에서는 이걸 참고해"라고 안내해서 필요한
것만 읽게 한다. 이 문서 자체가 그 예다 — POLICY.md는 항상 로드되지만 이 파일은 백틱 경로로만
언급되어 있어 필요할 때만 읽힌다.

### 3. Planning — 모호함을 코드로 옮기지 않는다
의도를 모른 채 실행하면 산출물이 아니라 재작업이 나온다. 모호한 지점은 질문으로 끌어내
요구사항과 태스크로 만든다. 계획은 파일로 남긴다(`.dev/plan/`) — 대화에만 있는 계획은
압축과 함께 사라지고 검토도 불가능하다.

사람의 승인이 필요한 이유는 권위 때문이 아니라 **가장 싼 교정 시점**이기 때문이다. 계획 단계의
오해는 한 문장으로 고쳐지고, 실행 후의 오해는 전체를 되돌린다.

### 4. Execution — 실행 방법 자체를 설계한다
계획을 이해했는지 확인하고 실행한다. 중요한 기능은 테스트로 먼저 동작을 확인한다(그러면
검증이 실행에 내장된다). 실행 방법을 영리하게 고민한다 — 독립적인 작업은 병렬로, 완료 기준이
명확하면 Ralph Loop 같은 반복 구조도 고려한다.

### 5. Verification — 자기검증은 검증이 아니다
자기가 쓴 코드를 자기가 검토하면 같은 사각지대를 반복한다. 그래서 외부 시선을 요구한다:
서브에이전트, 다른 기업의 모델(codex, copilot 등)의 비판적 검증, 브라우저 제어나 MCP로 실제
화면 확인, 스크린샷, 부작용이 예상되면 dry-run.

사람에게 의존하는 검증은 되도록 피한다 — 느리고 병목이 된다. **반복적이고 빠른 검증이 우선**이다.
컨텍스트에 이미 있는 검증 수단을 먼저 찾아보고, 적절하면 도입한다.

하네스는 이 단계에서 증거 없이 턴을 끝내지 못하게 막는다. 증거로 인정하는 것: 테스트/린트/타입체크
명령 실행, 서브에이전트 호출, 브라우저 계열 MCP 도구 사용, `--dry-run` 실행.

### 6. Compounding — 흔적을 자산으로 바꾼다
무엇이 잘못됐고 무엇을 배웠는지 기록한다. 그리고 한 단계 더 나아간다:

- 같은 **작업**이 반복되면 → 스킬이나 커맨드로 추출하는 것을 논의한다.
- 같은 **실수**가 반복되면 → Scaffolding 단계에서 훅이나 다른 장치를 고려한다.

기록만 하고 승격하지 않으면 복리가 아니라 일기다.

그리고 이 단계에서 **작업이 끝났는지 스스로 판단한다.** 두 갈래가 있다.

| 판단 | 명령 | 결과 |
| --- | --- | --- |
| 작업이 끝났다 | `advance --done` | 작업을 닫고 0번으로. 새 작업을 정한다 |
| 후속 회차가 남았다 | `advance --cycle` | 1번으로. **같은 작업을 유지하고 회차만 올린다** |

이 갈래가 "한 작업이 여러 회차에 걸친다"를 표현한다. 하네스는 어느 쪽인지 판정하지 않는다 —
작업이 끝났는지는 사람과 모델만 안다. 그래서 게이트가 아니고, 맨손 `advance` 는 두 선택지를
보여주고 멈춘다.

회차가 바뀌면 계획·검증 증거가 초기화된다. 초기화하지 않으면 2회차 Planning 이 1회차
계획서로 통과한다. 작업 선정 기록(`intent_set`)과 완료 조건(`acceptance`)은 남는다 —
작업은 그대로이므로 다시 정할 필요가 없다. 이전 회차의 계획·회고 **파일은 그대로 남고**, 파일명의 회차로 구분된다.

## 상태와 시퀀스: 왜 해시이고, 왜 DB를 커밋하지 않는가

한 작업이 `260804-a3f9c1` 같은 해시로 식별되고, 1~6단계를 여러 회차 돌 수 있다.
이 해시가 `.dev/` 산출물 파일명의 접두사가 된다.

`001, 002` 처럼 증가하는 번호를 쓰지 않는 이유는 **다음 번호를 알려면 다른 워크트리의
상태를 읽어야 하기 때문**이다. 병행 작업 중인 두 워크트리는 서로를 볼 수 없으니 둘 다
`003` 을 만들고 머지 시점에 충돌한다. 해시는 조정이 필요 없다.

상태는 `.claude/harness/harness.db` (SQLite)가 갖는다. 이 DB의 역할은 딱 두 가지다 —
**해시 발급과 현재 상태 제어.** 작업이 닫히면 그 작업의 행은 버린다. 영구 기록은 각 폴더에
남은 파일이고, 파일명이 해시를 갖고 있으니 그게 시퀀스이자 인덱스다.

그래서 DB는 커밋하지 않는다(gitignore). 얻는 것:

- 워크트리마다 자기 단계를 독립적으로 갖는다. 다른 브랜치의 "현재 단계"가 머지로 흘러들어오지 않는다.
- 바이너리 파일이 git 히스토리를 불리지 않는다. 머지 충돌도 원리적으로 없다.
- 지워도 된다. `harness status` 가 새 작업을 만들고, 기존 해시로 되돌아가려면
  `harness loop adopt <해시>` 를 쓴다.
- 병렬 툴 호출로 훅이 동시에 발화해도 트랜잭션이 쓰기를 직렬화한다. 단일 JSON 파일이었다면
  read-modify-write 경합으로 증거가 유실됐다.

**한 가지 대가**: 스킵된 단계는 파일을 남기지 않으므로, 작업이 닫히면 "무엇을 왜 건너뛰었나"만
사라진다. 그래서 Compounding 진입 시 하네스가 스킵 기록을 노출한다 — 회고 md 로
옮겨 적으면 그 사실이 git 에 남는다. 회고는 원래 그걸 적는 자리다.

## 엔진은 프로젝트 안에 두고, 하네스 자신은 잠근다

`init` 이 엔진 사본을 `.claude/harness/bin/harness.py` 에 둔다. 래퍼는 플러그인 원본을
먼저 실행하고, 원본을 찾지 못할 때만 이 사본을 폴백으로 쓴다. 사본은 gitignore 되고
세션 시작마다 갱신되므로 플러그인 버전과 어긋나지 않는다.

**왜 사본을 두는가.** 모델이 실행하는 명령이 작업 디렉터리 밖의 파일을 가리키면 막힌다 —
auto-mode 안전성 분류기와 샌드박스가 각각 한 번씩 실제로 막았다. 두 번 모두 같은 원인이었다.
훅은 Bash 툴을 거치지 않으므로 영향이 없었고(플러그인 캐시에서 그대로 실행된다), 막힌 것은
모델이 치는 CLI 뿐이었다.

**그래서 잠금이 필요해진다.** 사본이 프로젝트 안으로 들어오면 `.claude/**` 는 `context`
클래스라 여러 단계에서 쓰기가 열린다. 즉 모델이 자기를 통제하는 엔진을 고쳐 게이트를
무력화할 수 있다. `folder_rules.protected_paths` 가 이것을 막는다:

| 경로 | 이유 |
| --- | --- |
| `.claude/harness/bin/**` | 엔진·래퍼를 고치면 게이트가 무력화된다 |
| `.claude/harness/harness.db` | 덮어쓰면 DB 가 손상되고, 손상 시 차단하지 않는 설계(세션을 벽돌로 만들지 않기 위한 것) 때문에 **게이트 전체가 조용히 꺼진다** |

이 차단은 `allow` 로도 열리지 않는다. 예외를 허용하면 잠금의 의미가 없다.

규칙 자체는 여전히 고칠 수 있다 — `stages.json` 과 원칙 문서는 열려 있다. **무엇을 강제할지는
바꿀 수 있고, 강제하는 장치는 못 바꾼다.** 이 구분이 잠금의 요점이다.

## 복리를 만드는 것: 관측 기록과 pull 조회

복리가 되려면 Compounding이 남긴 것을 다음 회차·작업의 Context가 읽어야 한다. 그 링크를
잇는 것이 `event` 테이블이다.

**모델의 자기신고를 쓰지 않는다.** 자기신고는 부정확하고 조작 가능하다. 훅은 이미 사실을
관측하고 있으니 판정에만 쓰고 버리지 말고 적립한다.

| 기록되는 것 | 무엇을 말해주나 |
| --- | --- |
| `block` (규칙별 차단) | 어떤 규칙에 반복적으로 걸리는가 → 규칙이 틀렸거나 습관이 틀렸다 |
| `skip` (단계별 스킵) | 늘 건너뛰는 단계 → 그 단계 정의가 이 프로젝트에 안 맞다 |
| `stop_gate` / `bypass` | 검증·회고를 습관적으로 빠뜨리는가 / 게이트를 얼마나 뚫는가 |
| `tool_fail` | 같은 명령이 같은 이유로 반복 실패 → "동일한 실수"의 가장 직접적 증거 |
| `edit` | 한 작업에서 같은 파일을 몇 번 고쳤는가 → 구조 냄새 |

작업이 닫혀도 `event` 와 작업 인덱스(해시·의도·기간)는 남는다. 버리는 것은 진행 중 상태
(`stage`, `evidence`, `wgrant`)뿐이다. event 를 버리면 복리의 원료가 사라진다.

### Context 는 밀지 않고 당긴다

Context 진입 시 상위 반복 항목을 자동으로 주입하는 것은 **이 문서의 Context 원칙을 위반한다** —
"전부 싣지 말고 필요한 것만 읽게 한다"인데, 무관한 과거 실수까지 컨텍스트를 먹기 때문이다.
이전 작업의 실수가 지금 작업과 무관하면 읽지 않아도 된다.

그래서 하네스는 **조회 인터페이스만** 제공한다. 무엇이 관련 있는지는 Selection에서 정한
task 를 근거로 모델이 판단한다.

```sh
harness recall <키워드|경로>   # 관련된 것만 당겨온다
harness stats                  # 전체 그림이 필요할 때
```

이벤트 조회는 정확하게(세는 것이므로), 회고 파일 검색은 넓게(읽을 후보를 고르는 것이므로)
매칭한다 — `src/api.ts` 로 조회하면 이벤트는 그 경로만, 파일은 `api` 를 다룬 산문까지 걸린다.

Compounding은 반대다. 막 끝낸 회차 자신의 기록은 무조건 관련 있으니 단계 진입 시 밀어준다.

### 무엇을 강제하지 않기로 했는가

아래는 구현이 빠진 것이 아니라 **넣지 않기로 결정한 것**이다. 완벽한 통제가 목표가 아니다 —
과잉 통제는 마찰만 늘리고, 마찰이 커지면 게이트를 끄게 되고, 그러면 하네스가 사라진다.

| 강제하지 않는 것 | 이유 |
| --- | --- |
| 계획의 **내용** 검사 | 좋은 계획인지는 판단이다. 파일 존재와 사람의 승인까지가 훅의 한계 |
| **무엇을** 검증했는지 검사 | 검증 수단 선택은 판단이다. 증거의 존재까지만 본다 |
| 승격의 **내용** 검사 | 무엇으로 승격할지, 실제로 훅을 고쳤는지는 판단이다. 결정을 요구하는 것까지가 훅의 한계 |
| 정리(`tidy`)의 실행 | 후보만 제시한다. 무엇을 지우고 무엇을 남길지는 판단이다 |
| **셸 간접 호출 차단** | 아래 "막지 못하는 것" 참고 — 원리적으로 닫을 수 없다 |
| **턴 종료의 무한 차단** | 상한이 있다. 아래 "차단 상한" 참고 |

### 막지 못하는 것: 셸 간접 호출

동의가 필요한 명령의 탐지는 `PreToolUse` 가 받은 **Bash 명령 문자열**에 대한 정규식이다.
따라서 경로를 변수에 넣어 호출하면 탐지를 피한다.

```sh
X=.claude/harness/bin/harness; "$X" skip verification --reason x   # 탐지되지 않는다
```

이건 고칠 수 없다. 문자열을 아무리 정교하게 봐도 셸의 표현력을 따라갈 수 없고, 실제 실행
프로그램을 알려면 훅이 프로세스 실행을 가로채야 하는데 `PreToolUse` 는 그 층이 아니다.

**다만 "간접 호출은 못 막는다"가 "직접 형태를 대충 본다"의 변명이 되지는 않는다.** 두 번째
적대적 리뷰에서 직접 형태 여섯 가지가 뚫려 있었다 — `find … -delete`, `find … -exec rm`,
`dd of=<경로>`, `printf >|<경로>`, `rm -rf` 로 상위 디렉터리 통째, 그리고 `loop new` 의
동의 게이트를 옵션 위치(`loop --reason=x new`)나 앞선 무해한 명령(`status; loop new`)으로
지나치는 것. 전부 변수 없이 경로를 그대로 쓴 형태라 막을 수 있었고, 막았다. 경계는
"셸 트릭"이 아니라 **"경로가 문자열에 그대로 보이는가"** 다.

그래서 이 하네스는 **적대적인 모델을 막는 장치가 아니다.** 규칙을 지키려는 모델이 실수로
어긋나는 것을 잡고, 어긋난 사실을 기록에 남기는 장치다. 우회는 막지 못하지만 우회 시도는
`block` 이벤트(`no_reason`, `bypass_mode`, `protected_bash`)로 남고 `stats` 에 드러난다 —
그것이 이 층에서 할 수 있는 전부다.

같은 이유로 이 우회 기록들은 **승격 후보에서 제외한다**(`promotion.exclude_rules`). 기계화할
습관이 아니라 규율 신호이고, 승격 절차에 넣으면 사용자가 봐야 할 사실이 결정으로 세탁된다.

### 턴 이어붙임: 무인 실행의 유일한 추진 장치

하네스는 원래 **반응만 하고 턴을 시작하지 않는다.** 훅은 도구 호출이나 턴 종료에 붙는 것이지
스스로 일을 시작할 수 없다. `Stop` 훅으로 턴 종료를 막으면 그 한계를 밀 수 있다 — 종료 조건을
다 채웠는데 단계가 남았으면 "멈추지 말고 이어서 진행하라"고 되돌린다.

**이걸 켤 수 있게 만든 조건이 진전 감지다.** 없이 켰을 때 첫 실험에서 모델이 불가능한 명령을
4회 반복하며 헛돌았다. 그래서 이어붙일 때마다 지문을 남긴다.

```
지문 = (현재 단계, evidence 수, 모델 활동 이벤트 수)
연속 2회 지문이 그대로면 → 이어붙이기를 멈추고 사람에게 물으라고 한다
```

지문에서 **하네스 자신이 남기는 기록은 뺀다**(`stop_continue`, `stop_gate`, `bypass`,
`cycle_close`). 빼지 않으면 이어붙임 이벤트가 이벤트 수를 늘려 지문이 매번 바뀌고, 진전
감지가 자기 자신을 진전으로 세면서 영원히 발동하지 않는다 — 실제로 그렇게 만들어서 5회
헛돌았고, 수동 실행에서 눈으로 보고 찾았다(당시 테스트는 이 경로를 덮지 않았다).

읽기만 한 턴은 지문이 그대로다. 그건 의도한 것이다 — 단계 종료 조건은 증거·모델 활동·단계
전이로만 채워지므로, 그 셋이 그대로면 종료에 가까워지지 않았다.

진전 감지가 있으니 **상한을 넉넉히 줄 수 있다**(기본 6회). 일이 실제로 진행되는 동안은 여섯
번 밀어주고, 헛도는 경우는 두 번에서 끊는다. 멈춘 사실은 `stop_stalled` 이벤트로 남아
`stats` 에 드러난다.

### plan mode 와 Planning: 확정한 뒤에 파일을 쓴다

Claude Code 의 plan mode 는 이 단계와 목적이 같다 — 건드리지 않고 파악하고 계획한다.
그런데 **plan mode 는 파일 쓰기를 막고, 하네스의 Planning 은 파일이 있어야 끝난다**
(`plan_file` 은 `.dev/plan/**/*.md` 에 대한 Write 로 적립된다). 그대로 겹치면 Planning 이
영영 끝나지 않는다.

순서를 뒤집으면 충돌이 사라진다.

```
plan mode 진입 → 계획을 사용자에게 제시 → 오가며 확정 → plan mode 종료 → 확정본을 파일로
```

부수 효과가 하나 더 있는데 이게 오히려 본질에 가깝다. **초안을 파일로 남기지 않게 된다.**
계획을 파일에 쓰면서 다듬으면 `.dev/plan/` 이 버려진 계획으로 차고, 나중에 `recall` 이
그것들까지 끌어온다. 확정본만 남기면 그 폴더의 신호 대 잡음이 유지된다.

**`ExitPlanMode` 를 승인 증거로 쓰지 않는 이유.** 그 도구는 사용자에게 계획을 보여주고
승인을 받으므로 `plan_approved` 로 삼고 싶어진다. 그러면 다이얼로그가 하나로 준다.
하지만 **사용자가 거절했을 때도 `PostToolUse` 가 뜨는지 확인하지 못했다.** 뜬다면 거절된
계획이 승인으로 기록되고, 그건 게이트가 사람 없이 열리는 것이다 — 적대적 리뷰가 두 번
찾아낸 바로 그 부류다. 그래서 지금은 **관측만 하고 응답의 모양을 `plan_mode_exit` 이벤트로
남긴다.** 한 번 실제로 돌려보고 거절 시의 모양을 확인한 뒤에 배선한다.

추측으로 게이트를 여는 것보다 다이얼로그 하나를 더 띄우는 편이 싸다.

### 승인을 요구한다면 무엇을 승인하는지 보여준다

`acceptEdits`(auto-mode)에서도 계획 승인은 다이얼로그를 띄운다. 그게 맞다 — **"편집을
자동 수락"은 "방향을 검토하지 않겠다"가 아니다.** 편집을 믿는 것과 계획을 안 읽는 것은
다르고, 계획 승인은 이 하네스에서 사람을 방해할 값이 있는 **유일한** 자리다(가장 싼 교정
시점이기 때문이다).

그런데 다이얼로그가 **파일 이름만** 보여주고 있었다.

```
계획 승인 요청: `harness approve-plan .dev/plan/260805-a3f9c1-1-plan.md`
승인하면 하네스 상태에 기록된다.
```

이걸 보고 누르는 것은 읽지 않고 찍는 도장이다. **마찰만 있고 정보가 없다.** 그리고 그렇게
남은 `plan_approved` 는 "사람이 계획을 검토했다"의 증거가 아니라 "사람이 버튼을 눌렀다"의
증거다 — 이 하네스가 자기신고를 쓰지 않겠다고 한 원칙에 정면으로 어긋난다.

지금은 계획 본문을 다이얼로그에 싣는다(앞 24줄·1400자, 넘으면 몇 줄이 생략됐는지 알린다).
파일이 없으면 그 사실을 경고한다 — 없는 계획을 승인하는 것은 그 자체가 결함이다.

일반화하면 이렇다. **승인을 요구할 자격은 무엇을 승인하는지 보여주는 데서 나온다.** 보여주지
않으면 그건 동의를 구하는 게 아니라 책임을 넘기는 것이다.

### 막을 때는 최적 행동을 함께 준다 — 그리고 Selection 은 후보를 내놓는다

무인 실행에서 Selection 에 새 작업이 없을 때, 하네스는 "사람이 작업을 주는 자리이니 물어라"
고 말했다. **무인 실행에는 물을 사람이 없다.** 게이트가 옳게 막았지만 다음 행동을 주지
않았으므로 루프는 거기서 끝났다.

더 근본적으로 틀린 전제가 있었다. **"새 작업이 없다"는 "할 일이 없다"는 뜻이 아니다.**
하네스는 자기 기록에서 할 일을 이미 알고 있다.

| 후보 | 어디서 오나 |
| --- | --- |
| 승격 결정이 밀려 있다 | `pending_promotions` — 여러 작업에서 반복된 항목 |
| 승격했는데 재발했다 | `maturity='regressed'` — 그 방법이 통하지 않았다는 증거 |
| 인덱스가 없거나 낡았다 | `tidy_report` |
| 닫힌 작업의 오래된 파일 / 병합 후보 | `tidy_report` |
| `LEARNED.md` 예산이 찼다 | `learned_lines` 대 상한 |

이 다섯은 전부 **복리를 유지하는 일**이고, 사람이 새 기능 작업을 주지 않아도 존재한다.
그래서 Selection 에 intent 가 없으면 `status` 와 단계 진입이 이것들을 **실행할 명령과 함께**
후보로 내놓는다. 무인 실행은 그중 하나를 골라 `loop intent` 로 기록하고 계속 돌 수 있다.

그래도 정말 아무것도 필요 없으면 멈추는 것이 맞다. 그건 **교착이 아니라 정상 종료**이고,
메시지에도 그렇게 적는다. `HUMAN_CRITERIA` 대기 메시지가 후보 개수를 함께 알려준다.

일반화하면 이렇다. **게이트가 "할 수 없다"만 말하면 그건 절반이다.** 무엇을 하면 되는지
함께 주지 않으면 모델은 안내받은 대로 같은 벽을 반복하거나(승인 요청 무한 반복이 그랬다)
거기서 멈춘다. 특히 사람이 위험을 미리 감수하고 자리를 비운 모드에서는, 하네스가 판단의
재료를 주는 쪽이 자기 목적에 맞다.

### bypassPermissions 는 "동의 불가" 가 아니라 "사전 승인" 이다

처음에 `bypassPermissions`(= `--dangerously-skip-permissions`)를 **"사람의 동의를 받을 수
없는 상태"** 로 읽고 동의 명령을 전부 거부했다. 게이트가 조용히 무력화되는 것을 막으려는
의도였다.

그 결과 도그푸딩에서 이렇게 됐다. `--dangerously-skip-permissions` 로 무인 실행을 돌리자
Planning 에서 `approve-plan` 이 거부되고, 하네스는 "권한 모드를 낮추고 다시 시도하라" 고
말했다. 모델은 산문으로 "승인하면 진행한다" 며 사람을 기다렸고 루프가 멈췄다.
**무인 실행 전용 모드에서 무인 실행이 불가능해진 것이다.**

읽기가 틀렸다. 그 플래그는 사람이 "묻지 말라" 고 **미리 결정한** 것이다. 모델이 스스로
승인하는 것과 사람이 세션 단위로 승인해 둔 것은 다르다. 지금은 `auto-skip on` 과 같은
취급을 한다 — **다이얼로그는 생략하되 사유는 필수이고 기록은 남는다.** 우회 사실은
`bypass` 이벤트로 적립되어 `stats` 와 `metrics` 의 회피 열에 드러난다.

**예외가 하나 있다: `auto-skip on`.** 그 효과는 `meta` 에 저장되어 **세션을 넘어 남는다**
(`--scope project` 면 이후 세션에도). 세션 단위 사전 승인으로 세션을 넘는 결정을 덮을 수는
없으므로, 이것만은 거부하고 사람의 판단을 요구한다.

일반화하면 이렇다. **권한 모드는 "사람이 지금 어떻게 관여하겠다고 했는가" 를 말해준다.**
그걸 "관여할 수 없다" 로 읽으면 하네스가 사람의 결정과 싸우게 된다. 게이트의 목적은 모델이
스스로 승인하지 못하게 하는 것이고, 사람이 이미 승인한 것을 다시 막는 것이 아니다.

### 묻지 않아야 할 것을 묻지 않는다

도그푸딩에서 승인 요청이 무한히 반복됐다. Selection 에 더 할 작업이 없을 때 모델이
`skip selection` 을 시도하면 이렇게 됐다.

```
skip selection  →  ask 다이얼로그  →  사용자 승인  →  "Selection 은 건너뛸 수 없다.
                   대신 `skip until:selection` 을 쓰라"  →  모델이 그대로 시도  →  ask  →  …
```

세 결함이 겹쳐 있었다.

1. **훅이 실행 가능성을 보지 않고 물었다.** 승인을 받아봐야 거부될 스킵인데 다이얼로그를
   띄웠다. 훅과 CLI 가 서로 다른 판정을 한 것이고, 이건 `loop new` 우회와 **같은 부류**다 —
   두 곳에서 같은 것을 따로 판단하면 어긋난다. 지금은 `skip_block_reason()` 하나를 둘이
   함께 쓴다.
2. **안내 메시지가 항상 실패하는 명령을 알려줬다.** `until:<X>` 는 X 의 **직전**까지
   이동하므로 `until:selection` 은 인덱스 -1 이 되어 늘 거부된다. 회차 중단용으로 쓰던
   문구를 Selection 에도 그대로 냈던 것이다. 지금은 상황을 갈라서 말한다 — Selection 에서는
   "사람이 작업을 주는 자리이니 그렇다고 말하고 멈춰라", 회차 중간에서는 `until:compounding`.
3. **턴 이어붙임이 그것을 증폭했다.** Selection 에 작업이 없으면 종료 조건 `intent_set` 이
   비어 있으니 Stop 훅이 "이어서 진행하라"고 되돌렸다. 모델은 만들 수 없는 것을 만들려
   애쓰고, 그 시도가 매번 다이얼로그가 됐다.

셋째가 원칙적으로 중요하다. **사람만 채울 수 있는 조건이 남았으면 밀지 않는다**
(`HUMAN_CRITERIA` — `intent_set`, `plan_approved`). Selection 에 작업이 없는 것은 교착이
아니라 **사람을 기다리는 상태**다. 계획 승인을 기다리는 Planning 도 같다. 이때 하네스는
턴을 끝내고 무엇을 기다리는지 말한다.

교훈은 한 줄로 줄 수 있다. **거부할 것을 승인받으려 하지 마라.** 승인 다이얼로그는 사람의
주의를 쓰는 자원이고, 결과가 정해진 일에 그것을 쓰면 그건 마찰이 아니라 고장이다.

### 차단 상한: 왜 무한히 막지 않는가

`Stop` 훅의 조건별 차단 횟수에는 상한이 있다(`stop_block_limits`, 승격은 2회). 상한을 넘으면
미충족 상태로 턴 종료를 허용하고 `bypass` 이벤트와 `systemMessage` 를 남긴다.

무한히 막으면 세션이 벽돌이 된다 — 조건을 충족할 방법이 없는 상황(예: 필요한 도구가 없다)에
빠지면 영원히 끝나지 않는다. 그래서 **턴 종료는 결국 열리지만 단계는 열리지 않는다.**
`advance` 는 계속 거부하므로 작업이 다음 단계로 가지는 못한다. 즉 상한은 "탈출구"가 아니라
"숨 쉴 틈"이다.
| 병렬 실행·Ralph Loop 강제 | 실행 전략은 판단이다 |
| Bash 완전 차단 | 오탐으로 정상 작업을 망치는 쪽이 더 해롭다. `python -c` 등은 통과한다 |

훅 · 스킵 제한 · 말머리 규칙이면 충분하다. 나머지는 원칙 문서와 사람의 판단에 맡긴다.

### 측정할 수 있는 것과 없는 것

수치는 **과정**을 측정한다 — 차단, 스킵, 실패, 재편집. **품질**은 측정하지 못한다.
"이 규칙에 12번 걸렸다"는 말할 수 있지만 "설계가 나빴다"는 말할 수 없다. 그건 회고 텍스트와
사람의 판단 영역이다.

## 왜 승격을 강제하는가 (기록 → 자산)

기록만 쌓는 시스템은 복리가 아니다. 이건 우리 의견이 아니라 관측된 결과다.

AGENTS.md·CLAUDE.md 를 가진 오픈소스 레포 100개를 조사한 연구에서 가장 흔한 설정 냄새는
**lint leakage 가 62%** 였다 ([arXiv:2606.15828](https://arxiv.org/abs/2606.15828)) — *린터나 훅으로 막을 수 있는 것을 산문으로 적어둔 것*. 두 번째는
context bloat 42%(216~1477줄까지 부풀었고, 커지면 초반 지시가 묻혀 무시된다). 흔한 악순환은
이렇다: 실수 → 규칙 한 줄 추가 → 잠시 나아짐 → 또 다른 실수 → 또 한 줄. 파일이 터진다.

우리는 이 냄새를 원리적으로 피할 수 있는 위치에 있다. **하네스 자신이 훅이기 때문이다.**
반복되는 실수를 산문이 아니라 기계로 옮길 수 있다. 그러려면 반복을 세는 데서 멈추면 안 된다.

### 세 가지 장치와 그 근거

| 장치 | 무엇을 하는가 | 어디서 온 발상인가 |
| --- | --- | --- |
| **실패 지점 주입** | 같은 도구 실패가 2번째면 그 자리에서 반복 횟수·이전 오류·관련 회고 파일을 알려준다 | [CODESKILL](https://arxiv.org/abs/2605.25430) 의 event-driven 회수 — 에러 메시지를 키로 **온라인** 회수하는 것이 작업 시작에 한 번 밀어넣는 것보다 효과가 컸다. 실패한 순간은 무엇을 물어볼지 이미 아는 유일한 순간이다 |
| **승격 결정 강제** | 여러 작업에서 반복된 항목은 Compounding 의 종료 조건이다. 승격하거나 사유와 함께 보류해야 끝난다 | [ExpeL](https://arxiv.org/abs/2308.10144) 의 중요도 투표(0이 되면 삭제), [cass](https://github.com/Dicklesworthstone/cass_memory_system) 의 성숙도(`candidate→established→proven`) |
| **예산과 정리** | `LEARNED.md` 는 줄 수 상한이 있고, `tidy` 가 삭제·병합 후보를 제시한다 | [CODESKILL](https://arxiv.org/abs/2605.25430) 의 skill bank 는 add/merge/**drop** 으로 **크기가 수렴**한다. 무한히 자라는 저장소는 실패한 저장소다 |

### 보류를 왜 승인 없이 허용하는가

`promote --decline` 은 사용자 다이얼로그를 띄우지 않는다. 게이트 우회가 아니라 **기록**이기
때문이다. 그러면 모델이 전부 보류하고 빠져나갈 수 있는 것 아닌가 — 맞다. 그래서 두 가지를 둔다.

1. **보류는 event 로 남는다.** `stats` 에 "승격 보류"로 드러나고 사용자가 본다.
2. **보류는 되돌아온다.** 보류한 항목이 이후 2개 작업에서 다시 걸리면 결정이 무효화되고
   (`regressed`) 목록에 다시 올라온다. 승격했는데 재발한 경우도 같다 — **그 승격이 통하지
   않았다는 객관적 증거**이기 때문이다.

여기서 다이얼로그를 요구하면 무인 실행이 회차마다 멈춘다. 승인은 면제하고 기록은 면제하지
않는 것이 이 하네스의 일관된 선택이다(스킵도 같다).

### 회고는 무엇을 묻고, 왜 형식이 기계적으로 중요한가

오랫동안 회고는 **파일이 있는지만** 봤고 무엇을 묻는지는 설계된 적이 없었다. 밀어주던 것이
전부 하네스 내부 사정이었다 — 어떤 규칙에 걸렸나, 어떤 파일을 다시 고쳤나. 그건 "왜 내
규칙을 어겼나"를 묻는 것이고, **"무엇을 배웠나"는 아무도 묻지 않았다.**

이제 세 가지를 묻는다. 각각 근거가 있다.

| 질문 | 왜 |
| --- | --- |
| **무엇이 통했나** | ExpeL 은 통찰을 성공·실패 **짝**에서 뽑는다. 우리는 실패만 기록했다(`tool_fail`, `block`) — 정작 다음에 필요한 건 해결 쪽이다 |
| **무엇을 잘못 가정했나** | 같은 오해가 다음 작업에서 되풀이된다. 실수의 목록보다 그 뿌리가 전이된다 |
| **이 회차를 싸게 만들었을 것은** | 복리의 정의 그 자체다. 이걸 묻지 않으면 회고가 사후 보고서가 된다 |

**그리고 형식이 기계적으로 중요하다.** 회고는 나중에 정규화된 명령·규칙 이름으로 **텍스트
검색**되어 찾아진다. 같은 사실을 담아도 그 토큰이 글자 그대로 없으면 영원히 안 찾아진다.
실험으로 확인했다 — 같은 내용의 회고 둘 중 `npm test` 를 담은 것만 제시됐고, 풀어 쓴 쪽은
`recall` 에도 실패 주입에도 걸리지 않았다. 파일 앞 `RECALL_READ_BYTES` 바이트만 읽으므로
**위치도** 중요하다.

그래서 단계 진입 시 **이 회차의 검색 키를 그대로 알려주고**, 회차를 닫을 때 그 키가
들어갔는지 확인해 알린다. **막지는 않는다** — 무엇을 쓸지는 판단이다. 확인 결과는
`retro_keys` 이벤트로 남는다.

경계는 여기서도 같다. **통찰의 질은 채점하지 않는다**(판단이다). **찾아지는지는 확인한다**
(기계적 사실이다). 확인에 쓰는 읽기 범위는 `recall` 이 쓰는 것과 **같은 상수**여야 한다 —
다르면 "들어 있다"는 확인이 거짓말이 된다.

### 시각 비교는 문자열이 아니라 절대 시각으로 한다

`at`, `recheck_at` 은 `2026-08-04T12:00:00+0900` 형태로 저장된다. 이걸 SQL `>` 로 비교하면
오프셋이 섞이거나 DST 전환이 있을 때 사전순과 실제 순서가 어긋난다 —
`2026-11-01T01:30:00-0500` 은 `2026-11-01T01:45:00-0400` 보다 **실제로는 나중인데** 문자열로는
작다. 워크트리를 다른 타임존 장비에서 열면 그대로 걸린다. 그래서 비교는 Python 에서 epoch 로
바꿔서 한다(`ts_epoch`). 한 항목의 이벤트 수는 작으므로 행을 가져와도 싸다.

재발 판정의 경계는 결정 시각 **+1초**다. 초 단위 정밀도라서 `>` 로 두면 같은 초의 이벤트를
영구히 놓치고, `>=` 로 두면 결정 직전의 이벤트가 결정을 즉시 무효화한다.

### 게이트는 저장된 성숙도를 믿지 않는다

`promotion.maturity` 는 표시용 캐시다. 게이트(`criterion_met`)와 `LEARNED.md` 생성은
**그 자리에서 다시 계산한다**(`is_regressed`). 저장값만 보면 `stats`/`tidy`/`promote` 를
아무도 실행하지 않은 세션에서 재발한 항목이 `established` 로 남아 Compounding 을 통과한다 —
실제로 그렇게 새어나갔고, 그게 이 기능의 핵심 절반이었다.

### 성숙도를 왜 결정론적으로 계산하는가

`established → proven` 은 "승격 후 재발 없이 작업 N개가 지났다"로만 판정한다. LLM 에게
"이 규칙이 좋은가"를 묻지 않는다. cass 가 큐레이션 단계에 의도적으로 LLM 을 넣지 않은 이유가
같다([cass_memory_system](https://github.com/Dicklesworthstone/cass_memory_system)) — LLM 이
자기 판단을 다시 판단하면 등급이 표류하고(context collapse) 근거 없는 확신이 쌓인다. 우리에게는 이미 객관 신호가 있다: **같은 이벤트가 또 걸리는가.**

### 복리를 어떻게 측정하는가 (그리고 무엇을 측정할 수 없는가)

`harness metrics` 다. 세 블록이고 **점수가 없다.**

**① 승격 생존율이 유일하게 엄밀한 측정이다.** "하네스 있기 전/후"는 비교할 수 없다 — 기준선이
없다. 하지만 **"이 규칙을 승격한 전/후"는 비교할 수 있다.** 각 승격은 개입 시점과 대상과
결과(그 뒤 또 걸리는가)를 모두 갖춘 하나의 실험이다. 종류별 재발률이 쌓이면 62% lint leakage
가설을 이 프로젝트 안에서 직접 검증하게 된다 — 훅으로 옮긴 것은 정말 안 걸리는가, 산문으로
적어둔 것은 정말 다시 걸리는가.

여기에 **주장 대비 사실**을 붙인다. `--as hook` 은 주장이다. 그래서 승격할 때 그 회차에 맞는
파일 변경이 실제로 있었는지 관측해 기록한다(`promote_verify`). 막지는 않는다 — 무엇을 어떻게
고칠지는 판단이다. 하지만 `변경관측 2/3` 이 나오면 세 건 중 한 건은 말만 한 것이다.

**② 마찰 지표는 교란된다.** 차단·반복실패·재편집은 이미 기록되지만 **작업 난이도를 통제할
방법이 없다.** "5회차가 1회차보다 차단이 적다"는 규칙이 좋아진 결과일 수도, 쉬운 작업이었을
수도 있다. 그래서 개별 비교가 아니라 구간 추세로만 읽고, 그마저 정황 증거다.

**③ 점수를 만들지 않는 이유가 이 설계의 핵심이다.** 차단 횟수를 목표로 삼으면 차단을 피하는
법을 배운다 — 아무것도 시도하지 않거나 `skip`·`bypass`·`--decline` 으로 빠져나가면 차단은
줄어든다. 마찰이 준 게 아니라 회피가 는 것인데 숫자는 똑같이 예뻐진다. 우리 하네스에는 그
탈출구가 다 있다. 그래서 마찰 지표와 **회피 지표를 반드시 같은 화면에 놓는다.**

**모드 사전 승인은 회피가 아니다.** `bypassPermissions` 로 돌리면 모든 동의 명령이 `bypass`
로 적립된다. 그걸 회피로 세면 무인 실행이 곧바로 "게이트가 연극이 되고 있다" 로 판정된다 —
사람이 그렇게 하라고 지시한 것인데 그 지시를 비난하는 셈이다. 그래서 `preauth` 열로 갈라
표에는 보이되 **판정에는 넣지 않는다.** 무인 실행의 양은 알아야 하고, 그것이 규율 문제로
읽혀서는 안 된다.

| 관측 | 해석 |
| --- | --- |
| 마찰 ↓ · 우회 → | 개선 신호 |
| 마찰 ↓ · 우회 ↑ | **회피**. 게이트가 연극이 되고 있다 |
| 마찰 → · 우회 ↑ | 규칙이 이 프로젝트에 맞지 않는다 |

`metrics` 가 이 판정을 자동으로 붙인다. 지표를 하나로 합치면 이 구분이 사라진다.

**측정하지 못하는 것**: 결과물의 품질, 그 회차가 필요했는지(끈질김인지 헛돎인지), 사람이 아낀
시간, 회고 텍스트의 가치. 즉 측정하는 것은 **마찰**이고 알고 싶은 것은 **가치**다. 마찰은
대리 지표일 뿐이며, 그 사실을 출력 맨 아래에 매번 적는다.

**표본 이야기**: 승격 종류별 재발률에 의미를 붙이려면 20~30건이 필요하고, `min_loops: 3` 이니
작업 수십 개를 돈 뒤다. 지금 만드는 이유는 데이터가 시간에만 쌓이기 때문이고, 동시에 답은
한참 뒤에 온다는 뜻이다. 표본이 20건 미만이면 `metrics` 가 비율을 믿지 말라고 경고한다.

### 왜 회차 경계에서 스냅샷을 남기는가

`close_loop` 이 `stage` 행을 지우므로 작업이 닫히면 회차별 비용을 되살릴 수 없다. 그래서
회차 경계(`advance --cycle`/`--done`)에서 그 회차의 집계를 `cycle_close` 이벤트 한 줄로
남긴다. `event` 는 작업이 닫혀도 살아남으므로 측정이 나중에 가능해진다.

스키마는 바꾸지 않았다 — 측정도 승격 검증도 **새 event 종류로만** 기록한다. 열을 추가하면
구버전 DB 에서 `no such column` 으로 하네스가 죽고, 마이그레이션은 하지 않기로 했다.

### `LEARNED.md` 가 `POLICY.md` 와 분리된 이유

둘 다 CLAUDE.md 앵커로 항상 로드되지만 소유자가 다르다. `POLICY.md` 는 사람이 정한 원칙이고,
`LEARNED.md` 는 하네스가 `promotion` 테이블에서 **생성한다**. 섞으면 손으로 쓴 것과 생성된
것이 구분되지 않아 어느 쪽도 안전하게 고칠 수 없다. 그래서 `LEARNED.md` 는 쓰기 금지 경로다.

## 스킵 자동 승인: 왜 켜는 것만 승인이 필요한가

`harness auto-skip on` 은 스킵의 동의 다이얼로그를 끈다. 급한 기간에 게이트가 방해가 될 때
쓰는 장치다. 비대칭이 하나 있다:

- **켜기는 사용자 승인이 필요하다.** 게이트 자체를 무력화하는 행위이므로, 이것까지 자유롭게
  허용하면 모델이 스스로 켜서 모든 스킵을 통과할 수 있다. 그러면 하네스가 아니다.
- **끄기는 승인이 필요 없다.** 게이트를 복원하는 방향이라 언제든 안전하다.

켜져 있어도 없어지는 것은 **다이얼로그뿐**이다. `--reason` 은 여전히 필수이고, 기록에는
`authorized_by=auto` 로 남아 사람이 승인한 스킵과 구분된다. 스킵이 자동 승인될 때마다
`systemMessage` 로 사용자에게 노출되고, `status` 와 세션 시작 컨텍스트에 `⚠ ON` 이 계속
표시된다 — 켜둔 사실을 잊는 것이 가장 위험하다.

**범위를 좁혀라.** `--uses N` 은 N회 후, `--scope loop` 는 작업이 바뀌면 자동 만료된다.
무제한으로 켜두는 것이 가장 위험한데, 게이트가 열린 것을 잊기 때문이다. 만료되면 `status` 가
이유까지 알려준다 — 사용자가 왜 게이트가 돌아왔는지 모르면 안 된다.

만료 판정은 플래그를 뒤집지 않고 계산으로 한다. 플래그(`auto_skip`)는 사용자의 **의도**를
담고, 실효 상태는 범위·횟수를 함께 보고 결정한다. 소진 시점에 플래그를 `off` 로 덮어쓰면
"왜 꺼졌는지"를 잃는다.

스킵이 자꾸 막혀 불편하다면 자동 승인을 켜기 전에 `stages.json` 이 이 프로젝트에 맞는지
검토하는 게 낫다. 게이트를 끄는 것보다 규칙을 고치는 것이 옳은 해결이고, 그게 Compounding
단계에서 할 일이다.

### 스킵은 승인을 면제하지만 기록을 면제하지 않는다

이게 무인 실행이 성립하는 조건이다. `stages.json` 의 `skip_requires` 에 걸린 조건은 스킵으로도
면제되지 않는다 — Planning 은 `plan_file` 이 걸려 있어서, 건너뛰더라도 계획 파일은 남아야 한다.

무인으로 회차를 열 번 돌았을 때 **계획 열 개가 남는 것과 스킵 기록 열 개가 남는 것은 복리의
재료로서 다르다.** 전자는 다음 회차의 Context 가 `recall` 로 당겨올 수 있고 Compounding 이
패턴을 볼 수 있다. 후자는 "건너뛰었다"만 남는다.

회고도 같은 원칙이다. Compounding 은 `skippable: false` 이고 `retro_file` 이 종료 조건이므로,
자동 승인이 켜져 있어도 회고 없이 그 단계를 벗어날 방법이 없다 — 건너뛰기도, 작업 종료도,
다음 회차로 넘어가기도 전부 막힌다.

정리하면 무인 실행은 **사람의 승인을 생략하는 것이지 기록을 생략하는 것이 아니다.** 사람의
결정은 Selection 에서 목표와 완료 조건으로 한 번 내려지고, 그 뒤로는 하네스가 기록을 강제하며
회차를 돈다.

## 정확하지 않은 통제는 제거한다

이 저장소가 가장 비싸게 배운 것이다. 순서대로 적는다.

Bash 명령이 **어느 경로에 쓰는지** 알아내려고 근사를 열아홉 번 고쳤다. 매번
다음이 있었다 — 셸의 부작용은 정적으로 결정 불가능하기 때문이다
(`.dev/shell-write-detection-is-undecidable.md`). 그래서 단계별 쓰기 규칙을
Bash 에서 **기록으로 내렸다**(0.71.0).

같은 일이 한 번 더 있었다. 인터프리터에 인라인으로 넘긴 코드를 되묻던 규칙을
두 번 좁혔는데, 좁힐수록 다른 데서 샜다.

| 어떻게 잡든 | 결과 |
| --- | --- |
| 느슨하게 | 우회는 잡지만 `.claude/*` 를 만지는 **정상 작업이 전부** 걸린다 |
| 정확하게 | 오탐은 없지만 원문 감시와 **완전히 중복**이다 |

중간이 없었다. 그리고 그 규칙은 **한 번도 막은 적이 없다** — `ask` 만 냈고,
`ask` 는 bypass 모드의 적대자에게 자동 승인이다. 적대자만 하는 행동을,
적대자에게는 통하지 않는 방법으로, 모든 정상 작업에 비용을 물려 가며 감시하고
있었다. 지웠다(0.73.0).

**규칙:**

> 엄격한 통제를 지향한다. 다만 **정확한 통제가 아니면 제거한다.**
> 올바른 통제만이 기능한다.

판단 순서는 이렇다.

1. **이 통제가 지금 무엇을 지키나** — 층이 바뀌면 답도 바뀐다. 옛 답을 믿지 않는다
2. **그것을 다른 층이 이미 잡고 있나** — 잡고 있으면 이 통제는 중복이다
3. **틀렸을 때 대가가 누구에게 가나** — 정상 작업이 내면 그 통제는 값보다 비싸다
4. **막기는 하나** — `ask` 만 내면서 적대자를 상정한 통제는 자기모순이다

셋 중 하나라도 걸리면 **좁히지 말고 지운다.** 좁히는 수정은 이 저장소에서 두 번
연속으로 다음 누수를 만들었다. 검사·방어를 더하는 수정보다 **합치거나 없애는
수정을 우선한다.**

## 하네스가 강제하는 것과 하지 않는 것

훅은 확정적인 사실만 판정할 수 있다. 그래서 역할을 나눈다.

**훅이 강제한다 (기계적으로 판정 가능)**

| 규칙 | 방식 |
| --- | --- |
| `docs/` 쓰기 | 차단 — 승인 시 예외 |
| 단계별 쓰기 허용 경로 | 차단 |
| 신규 최상위 폴더 | Scaffolding 외 차단 |
| `.dev/` 하위 폴더명, `docs/**/NNN-name.md` | 차단 |
| `.dev/` 파일명에 `<작업해시>-<회차>-` 접두사 없음 | 차단 |
| 계획 파일 + 사람의 승인 없이 Planning 종료 | `advance` 거부 |
| 검증 증거 없이 Verification 종료 | 턴 종료 차단 · `advance` 거부 |
| 회고 기록 없이 Compounding 종료 | 턴 종료 차단 |
| 사유 없는 스킵 | 차단 · 사유 있으면 사용자 승인 다이얼로그 |
| 말머리에 단계 미표시 | 턴 종료 차단 |

턴 종료 차단에는 상한이 있다(`stages.json` 의 `stop_block_limits`). 무한 루프를 막기 위한
것이고, 상한을 소진해 통과할 때는 **`systemMessage` 로 사용자에게 그 사실을 노출한다** —
조용한 우회가 없는 게 상한을 없애는 것보다 중요하다.

**훅이 판정하지 않는다 (판단 영역)**

계층적 컨텍스트를 잘 짰는지, 병렬 실행이나 Ralph Loop이 적절한지, 검증 수단 선택이 타당한지,
스킵 사유가 합리적인지, 구조 변경이 지금 옳은지. 훅은 "합리적인 이유"를 판정할 수 없다.
그래서 사유의 **기록**만 강제하고, 판정은 사람에게 넘긴다. 이게 훅으로 가능한 최대치이고
동시에 감사 가능한 형태다.

## 엔진은 조건의 이름을 몰라야 한다 (어휘와 문서의 분리)

`stages.json` 은 처음부터 설정 파일이었지만, 엔진 곳곳에 **조건의 이름과 단계의 이름이
박혀 있었다.** `EVIDENCE_STAGES = ("execution", "verification")`, `HUMAN_CRITERIA`,
`CRITERIA_HELP` 사전, `if kind == "promotion_decided"`, `if sid == "scaffolding"`.
그래서 단계를 더하거나 조건을 바꾸려면 파이썬을 고쳐야 했고, 실제로 0.10.0 에서
Selection 을 신설했을 때 이 부류가 낡아 모델이 틀린 단계를 보고했다.

엔진이 알아야 하는 것은 **판정 방식**이지 조건의 이름이 아니다. 그래서 `criteria` 어휘를
두고 `satisfied_by` 로 방식만 고르게 했다.

| `satisfied_by` | 판정 |
| --- | --- |
| `cli` | 사람·모델이 명령으로 기록한다 (evidence 행) |
| `file` | 산출물이 디스크에 있으면 충족 — 관측이 필요 없다 |
| `observed` | 도구 사용을 관측해 적립한다 (실패한 실행은 제외) |
| `no_pending_promotions` | 프로젝트 전체의 미결 승격이 없으면 충족 |

`human: true` 는 "사람만 채울 수 있다"는 표시이고, 그 조건이 남았으면 턴을 밀지 않는다.
거부 메시지(`help`)도 데이터다 — 우리 설계 원칙 중 "막을 때는 최적 행동을 함께 준다"가
스키마로 강제된다. 단계 진입 시 무엇을 보여줄지도 `stages[].panels` 가 정한다.

그래서 이제 **없던 조건을 새로 정의하는 것이 설정 편집이다.** 예를 들어 Planning 의 종료
조건을 `design_doc` 으로 갈아끼우려면 `criteria` 에 항목을 하나 넣고 그 단계의
`exit_criteria` 를 바꾸면 된다. 엔진은 그 이름을 모른 채 게이트를 세운다.

여기에 전제가 하나 필요했다. `init` 은 **기존 `stages.json` 을 덮지 않는다** — 사용자가
고친 문서이기 때문이다. 그래서 새 어휘를 넣으면 기존 설치는 영원히 받지 못하고, 그건
게이트가 조용히 어긋나는 것이다. `load_config` 이 **없는 최상위 영역만** 템플릿에서 채운다.
영역 **안의** 항목은 채우지 않는다 — "마찰이 크면 `stages.json` 에서 덜어낸다"가 이
하네스의 작업 방식이고, 항목 단위로 병합하면 지운 것이 되살아나 그 자유를 빼앗는다.

이름을 바꿨으면 옮겨주는 것도 포함이다. `evidence_signals` 를 커스터마이즈한 문서
— 예컨대 `bash_pattern` 에 자기 빌드 명령을 넣어 둔 경우 — 는 그 값을 `criteria` 로
이월한다. 옮겨주지 않으면 사용자는 자기 설정이 사라진 것을 모른 채 검증 게이트가 안
열리는 것만 보게 된다.

### 쓰기 규칙도 데이터다

폴더·파일명 규칙 일곱 개가 파이썬 함수였다. 뜯어보니 **전부 같은 모양**이었다.

```
가드:  class == X  [· 깊이 ≥ N]  [· parts[1] ∈ <설정목록>]  [· basename ∉ <면제>]
판정:  일곱 가지 중 하나
```

선택자 다섯 개(`class`·`min_depth`·`subdir_in`·`basename_not_in`·`creates_new_toplevel`)와
판정 일곱 개(`never`·`not_matching`·`class_in_stage_write`·`stage_in`·`subdir_in`·
`basename_starts_with`·`basename_matches`)로 **일곱 규칙이 전부** 들어갔다. 파이썬은
접착제였을 뿐이고, 이미 설정 키를 읽고 있었다.

```jsonc
{ "id": "loop_prefix",
  "when":    { "class": "dev", "min_depth": 3,
               "subdir_in": "loop_prefixed_dirs",
               "basename_not_in": "prefix_exempt_names" },
  "require": { "basename_starts_with": "<loop_prefix>" },
  "deny":    "이 작업의 산출물은 … '{basename}' 대신 '{prefix}{basename}' 로 써라 …" }
```

**배열 순서가 우선순위다.** 규칙 순서를 뒤집는 변이를 넣어 보니 하네스 자기 보호가
뚫렸다 — 순서가 장식이 아니라는 증거다. 예전 92줄 if-체인에서는 그 순서가 코드 흐름에
숨어 있었다.

거부 메시지가 데이터가 된 것이 부수 효과 이상이다. 우리 원칙 중 "막을 때는 최적 행동을
함께 준다"가 **스키마로 강제된다**(`deny` 가 없으면 진단이 지적한다). 그리고 차단은
규칙 `id` 로 적립되므로 **새로 만든 규칙이 곧바로 `stats`·승격 대상이 된다** — 설정 한
항목을 더하면 복리 장치가 그것을 따라온다.

정직하게 적어둘 것: **엔진 줄 수는 줄지 않았다**(83줄 늘었다). 술어 89줄이 빠지고
범용 평가기와 진단이 들어왔기 때문이다. 이 작업의 이득은 코드량이 아니라 **규칙 하나를
더하는 한계비용**이다 — 파이썬 함수를 쓰고 표에 등록하던 것이 JSON 항목 하나가 됐다.
판정 비용은 쓰기당 9–15 µs 로 훅 한 번(약 70ms)에서 무의미하다.

어휘로 표현할 수 없는 규칙은 `"require": {"predicate": "<이름>"}` 으로 파이썬에 남긴다.
**탈출 해치를 처음부터 넣은 이유**는 규칙 DSL 의 고전적 실패가 둘 중 하나이기 때문이다 —
너무 약해서 필요한 규칙을 못 쓰거나, 어휘를 늘리다 튜링 완전해져서 파이썬으로 쓰는 것과
같아진다. Cupcake 가 자체 문법 대신 Rego 를 고른 것도 같은 이유다. 해치가 비어 있는 것이
정상이고, 거기 무언가 들어가면 **그것이 다음 어휘 후보 목록**이다.

### 정책과 내용은 설정, 기계는 코드

무엇이 어휘가 되어야 하나. 기준은 **"엔진이 이 단어를 알아야 하나"** 다. 알아야 하는 것은
코드에 남고(도구 이름, 훅 이벤트, 파싱, 판정 방식 자체), 사람이 정하는 것은 설정으로 간다.
그 기준으로 다섯 개를 옮겼다.

| 어휘 | 왜 사람이 정해야 하나 |
| --- | --- |
| `recall.dirs` | 어느 폴더의 기록을 다시 읽을지. **`dev_subdirs` 전체를 읽지 않는 것이 의도다** — `plan`·`log`·`scratch` 는 교훈이 아니라 산출물이고, 끌어오면 조회가 소음에 덮인다 |
| `retro_questions` | 무엇을 묻는지가 회고의 값을 정한다. 프로젝트마다 비싼 실수가 다르다 |
| `consent` | 어느 행위에 사람의 승인이 필요한지. **설정이라는 것은 덜어낼 수 있다는 뜻이다** — `allow` 다이얼로그가 시끄러우면 하네스를 끄는 대신 그 항목을 뺀다 |
| `bash.mutator_pattern`·`readers` | 툴체인이 프로젝트마다 다르다. `just`·`task` 를 쓰는 저장소에서 기본 목록은 틀렸다 |

`recall.dirs` 는 어휘화 이전에 **조용한 결함**이었다. 문서는 "마찰이 크면 `stages.json` 을
고쳐라"라고 안내하는데, `dev_subdirs` 에 `postmortem` 을 더해도 `recall` 은 그 폴더를
보지 않았다. 파일은 있고 키워드도 맞는데 조회에 영원히 안 걸린다 — **다시 안 읽히는 기록을
쌓게 만드는 것**이고, 복리의 정확한 반대다. 실제로 재현해 확인했다.

동의 어휘에는 예외가 하나 있다. `auto-skip on` 은 `consent` 를 통째로 비워도 계속 묻는다.
그 효과가 세션을 넘어 남으므로 "이번 한 번"의 판단이 아니기 때문이다. 이건 설정으로 내리지
않았고, 내리지 않은 이유를 여기 적어 둔다.

`bash.mutator_pattern` 은 **보호 경로의 부모 디렉터리**를 대상으로 할 때만 좌우한다
(`rm -rf .claude`). 보호 경로를 직접 지정하면 패턴과 무관하게 막힌다 — 모르는 명령이
하네스를 건드리는 쪽이 fail-safe 여야 한다. 잘못된 정규식을 넣으면 기본 패턴으로 되돌아가고
진단이 그 사실을 말한다. 설정 오류로 게이트가 열리는 일은 없어야 한다.

### 성숙도 상태 기계는 어휘로 내리지 않았다

승격 층에서 **조절 가능한 정책은 이미 전부 설정**이다 — `min_loops`, `max_per_cycle`,
`proven_after_loops`, `reopen_after_loops`, `learned_max_lines`, `exclude_rules`,
`verify_globs`, `verify_exclude`, 그리고 `as_kinds`. 승격의 **종류**까지 설정으로
내렸으므로(`test`·`lint` 같은 종류를 쓰는 팀이 있다) 남은 것은 상태 기계의 **모양**뿐이다.

```
established ─(N개 작업에서 재발)→ regressed
established ─(재발 0 + M개 작업 경과)→ proven
```

이건 내리지 않았고, 왜 안 했는지를 적어 둔다.

**첫째, 별개의 언어가 필요하다.** 쓰기 규칙은 "경로에 대한 술어"라서 선택자 5개와 판정
7개로 닫혔다. 상태 기계는 이벤트 이력에 대한 **질의 + 시간창 + 임계값**을 표현해야 하고,
그건 같은 어휘로 안 된다.

**둘째, 인스턴스가 하나다.** 쓰기 규칙은 일곱 개를 나란히 놓고 공통 모양을 찾았다. 여기는
상태 기계가 하나뿐이다. 하나를 보고 문법을 만들면 **그 하나의 우연을 문법으로 굳힌다** —
어휘화를 시작한 이유와 정반대 방향이다. 두 번째 하네스가 생기면 무엇이 공통인지 관측으로
드러나고, 그때 하면 된다.

`TREND_KEYS`(측정 표시 라벨)도 여기 두지 않았다. 키는 카운터 이름(기계)이고 값은 표시
문자열(번역 대상)이다. 규칙 파일에 번역 문자열을 넣는 것은 집이 틀렸다 — 그건 메시지
카탈로그의 자리다.

### 출력 문자열도 데이터다 (원문이 키다)

거부 메시지·회고 질문·동의 설명이 설정으로 나가면서 흐름이 하나 생겼다. 그 완성이
메시지 카탈로그다. 엔진의 출력 문자열에 설정에서 온 문장을 더해
**전부가 한 파일**로 모인다.

키를 따로 발명하지 않는다. **원문이 곧 키다**(gettext 방식). 키를 만들면 키와 문장이
어긋나고, 어긋난 것을 아무도 모른다. 그리고 카탈로그에 없으면 원문을 돌려주므로
**번역이 없거나 일부만 있어도 동작이 바뀌지 않는다** — 그게 `t()` 의 계약이다.

서식 문자열은 리터럴 자리에서 감싼다: `t("현재 %s") % x`. 보간 뒤에는 원문을 찾을 수
없으므로 출력 지점에서 번역할 수 없다. 190개가 서식 문자열이었다.

**어떻게 313곳을 감쌌나.** 손으로 하면 반드시 빠지고, 빠진 것을 아무도 모른다. 그래서
AST 가 주는 정확한 위치로 소스를 잘라 붙였다(`ast.unparse` 는 주석을 지우므로 쓰지
않는다 — 이 코드베이스에서 주석은 본문이다). 그리고 **완전성을 기계가 검사한다** —
`tests/msg_check.py` 가 감싸지 않은 한글 리터럴을 전수로 찾고, `gen_catalog.py` 가
카탈로그를 코드에서 생성한다. 사람이 세는 일이 아니다.

세 가지가 실제로 걸렸고 전부 기계가 잡았다.

- `col_offset` 은 **문자 인덱스가 아니라 UTF-8 바이트 오프셋**이다. 한글이 3바이트라
  문자 기준으로 계산하니 닫는 괄호가 두 줄 아래에 꽂혔다 — `ast.parse` 가드가 잡았다.
- 지역 변수 `t` 를 쓰는 함수가 열한 개 있어 전역 `t()` 를 가렸다. 감싸기보다 **먼저**
  이름을 바꿔야 했다 — 순서를 틀려 감싼 호출까지 이름이 바뀌었다.
- 검사기와 생성기가 각자 문자열을 모아 기준이 어긋났다. 추출 로직을 `_msgs.py` 한 곳에
  모았다. 같은 것을 두 곳에서 계산하면 어긋난다 — 이 저장소에서 반복해 겪은 부류다.

언어는 `stages.json` 의 `language` 또는 `HARNESS_LANG` 로 정한다. 카탈로그가 없거나
일부만 있으면 **그 사실을 말한다** — `language: en` 을 켰는데 전부 한국어로 나오면 켠
사람은 그것을 '번역이 없다'가 아니라 '설정이 안 먹었다'로 읽는다. 카탈로그가 깨져도
원문으로 동작한다. 번역 때문에 게이트가 멈추는 것은 어떤 번역 누락보다 나쁘다.

### 진짜 경계는 어디인가 (버그의 형태가 알려준 것)

적대적 리뷰 두 차례가 자기 잠금 우회를 **열 가지 넘게** 찾았다. 하나씩 막다 보니
막을 때마다 새 표기가 나왔다 — 대소문자, `db-journal`, 디렉터리 자체, symlink,
`python3 -c "open(...)"`, `p=경로; printf x > "$p"`. 덧칠이 끝나지 않았다.

그래서 형태를 봤다. **나는 "이 문자열이 보호 파일을 가리키나"를 파싱으로 판정하려
했다.** 셸은 튜링 완전하고 파일시스템에는 별칭이 있으므로 그 판정은 결정 불가능하다.
패턴을 하나 더할 때마다 다음 표기가 통과한다.

그리고 더 중요한 것을 확인했다. **훅은 전부 `${CLAUDE_PLUGIN_ROOT}` 의 플러그인
엔진을 실행한다.** 프로젝트 사본(`.claude/harness/bin/harness.py`)은 CLI 편의용이고
`refresh_engine` 이 세션마다 덮는다. 사본을 쓰레기로 만들어도 판정은 그대로 돌아간다 —
직접 확인했다. 즉 **내가 열심히 지키던 것은 게이트가 아니었다.**

진짜 자산은 `harness.db` 다. 그것을 못 읽으면 모든 게이트가 한꺼번에 꺼진다.
그런데 예전에는 stderr 한 줄만 남기고 조용히 통과시켰다. 세션을 벽돌로 만들지 않으려는
fail-open 은 맞지만, **꺼진 사실을 숨기는 것은 fail-open 이 아니라 은폐다.**

그래서 구조를 이렇게 바꿨다.

| 예전 | 지금 |
| --- | --- |
| 문자열을 파싱해 우회를 예측 | 바닥값은 유지하되 **더 이상 확장하지 않는다** |
| 사본을 지키려 애씀 | 사본은 지키지 않는다 (게이트가 아니다). 세션마다 복원될 뿐 |
| DB 손상 시 조용히 통과 | **매번 "모든 게이트가 꺼졌다" 고 말한다** (판정은 여전히 열어 준다) |

**경계를 정직하게 적어 둔다.** PreToolUse 경로 규칙은 **실수를 막는 가드레일**이지
작정한 우회를 막는 보안 경계가 아니다. `stages.json` 은 `context` 클래스라 모델이
쓸 수 있고, 셸은 무엇이든 표현할 수 있다. 이것을 보안 경계로 만들려면 층을 내려가야
한다 — git pre-commit, OS 샌드박스(**어느 층이 강제하나** 절 참고). 그 값을 치를
이유가 생기기 전까지는 가드레일로 쓰고, 가드레일이라고 부른다.

### 내가 틀린 것: 사본은 게이트가 맞았다

0.37.0 에서 "프로젝트 엔진 사본은 게이트가 아니다"라고 적었다. 훅이 플러그인 엔진을
실행하는 것은 맞지만, **`.claude/settings.json` 이 그 래퍼를 사전 승인한다**
(`SAFE_PERMS`). 래퍼가 사본을 먼저 실행하고 있었으므로, **사본을 덮는 것이 곧
승인 없는 임의 코드 실행**이었다. 3차 리뷰가 지적했고 맞다.

고친 것은 래퍼의 순서다. **권위 있는 원본을 먼저 쓰고 사본은 폴백으로만 쓴다.**
모델이 치는 명령은 여전히 작업 디렉터리 안의 래퍼이므로 분류기 문제도 생기지 않는다.
사본을 악성 코드로 덮어도 원본이 판정하는 것을 확인했다.

그리고 "훅은 프로젝트 밖 엔진을 실행한다"는 주장 자체가 `git` 소스에서만 참이다.
`directory` 소스로 등록하면(README 가 로컬 테스트에 권하는 방식) 플러그인 루트가
프로젝트 안이 된다. **문서에 주장을 적어두면 설치 형태가 바뀔 때 거짓이 된다.**
그래서 런타임에 재어 말한다 — "플러그인 엔진이 프로젝트 안에 있다. 이 설치
형태에서는 자기 잠금을 신뢰할 수 없다. 개발 중이면 정상이다."

**패턴이 같다: 주장하지 말고 측정하라.** 자기검사도, 설치 형태도, 스코프 분석도.

### 한 종류가 두 뜻을 가지면 갈라야 한다

`cycle_close` 는 **측정 창의 경계**이자 **회차 스냅샷**이었다(`_cycle_rows` 가
`detail` 을 JSON 으로 파싱한다). 재연결에 그 종류를 썼더니 두 가지가 깨졌다 —
이전 회차의 측정치가 창에서 빠지면서 기록되지도 않았고, 재연결 사유가 JSON 처럼
생기면 **가짜 회차로 집계**됐다.

재연결의 목적은 접두사를 바꾸는 것이지 회차를 닫는 것이 아니다. `cycle_adopt` 로
갈라, 회차 번호는 올리되 측정 창은 건드리지 않는다. `loop adopt` 에서 겪은 것과
같은 형태다 — 거기서는 `cycle` 이 접두사 구분자와 창 번호를 겸했다.

### 대리 지표를 버린다 (세 번 틀린 뒤에 배운 것)

"강제가 실제로 작동하나" 를 세 번 다른 방식으로 추정했고 **세 번 다 거짓말했다.**

| 시도 | 어떻게 무너졌나 |
| --- | --- |
| ① 무력화 모양을 예측해 진단 | 리뷰가 새 모양을 계속 찾았다 (빈 목록, 이름 바꾸기, `(?!)`, 조건 배열 비우기…) |
| ② 규칙·조건 **개수**를 세어 보여줌 | 있지만 죽은 규칙 7개가 "쓰기 규칙 7" 로 세어졌다 |
| ③ "발동 가능" 만 세도록 보정 | 거짓값 조건이 여전히 발동 가능으로 세어졌다 |

셋 다 **설정을 들여다보고 결론을 추정**한 것이다. 설정이 강제를 무력화하는 방법은
내가 아는 것보다 항상 많으므로, 추정은 한 발 늦는다. 이 패턴이 세 라운드에 걸쳐
64건의 절반을 만들었다.

이미 두 번 옳은 답을 냈는데 끝까지 밀지 않았다 — `bash_pattern` 은 실제 명령으로
**탐침**했고, 스코프는 파이썬의 **실제 분석기**(`symtable`)를 썼다. 그 원칙을 완성한다.

**대표 조작을 실제 판정 함수에 넣고 결과를 본다.**

```
자기검사: N/N 통과 (대표 조작을 실제 판정에 넣어 확인)
```

규칙을 죽이면 이렇게 된다.

```
⚠ 자기검사 1/N 실패 — 강제가 기대와 다르게 동작한다:
  - .dev/ 산출물 접두사 → 통과
```

이건 대리 지표가 아니라 **강제 그 자체를 돌려 본 것**이므로 거짓말할 수 없다.
그리고 바닥값이 버티는 경우(`protected_paths` 를 비웠지만 엔진은 여전히 막힘)에는
`통과` 가 나오는데, 그건 오진이 아니라 **사실**이다 — 개수 요약은 여기서도 틀렸다.

종료 조건도 같은 방식으로 본다. `plan_approved` 의 글롭을 `**` 로 넓히면 "무관한
경로도 받는다" 고 말하고, `bash_pattern` 이 `true` 나 `ls` 를 받으면 그것을 말한다.
Codex 가 "탐침 네 개를 피하는 패턴이 있다" 고 지적한 것도 이 방식으로 잡힌다 —
탐침 목록은 늘리면 되고, **판정 자체를 돌리는 구조는 바꾸지 않아도 된다.**

### 검사기도 검사해야 한다

자기검사가 주 신뢰 장치가 되자 **탐침 누락이 곧 조용한 구멍**이 됐다. 그걸 내
판단으로 지키면 또 놓친다 — 세 라운드가 그랬다.

두 가지를 발견했다. 첫째, 탐침 결과가 **지금 어느 단계인가에 좌우됐다.** Selection
에서는 `stage_write` 가 거의 전부를 막으므로, 다른 규칙이 죽어도 탐침이 통과한다 —
막히긴 하되 **다른 이유로**. 그래서 탐침마다 그 규칙이 유일한 차단자인 단계를
고정했다. 둘째, `docs_naming` 은 예외(`allow`)가 있어야 도달하는데 자기검사가 상태를
바꿀 수는 없으므로, 가짜 grant 를 끼워 판정만 돌린다.

그리고 **메타 테스트**를 넣었다. 규칙을 하나씩 죽여 자기검사가 알아채는지 기계가
확인한다. 규칙을 새로 더하면서 탐침을 잊으면 거기서 실패한다.

일곱 규칙 중 여섯이 잡히고, `docs_readonly` 하나는 잡히지 않는다. **그건 결함이
아니라 사실이다** — 기본 설정의 어떤 단계도 `docs` 쓰기를 허용하지 않으므로
`stage_write` 가 먼저 막고, 예외가 있으면 둘 다 `grant_opens` 라 함께 열린다. 지워도
결과가 바뀌는 상태가 없다. 다만 **죽은 코드는 아니어서**, `docs` 를 허용하는 단계를
만들면 유일한 차단자가 된다 — 그 상태를 테스트가 직접 만들어 확인한다. 예외를
"중복이다" 한마디로 넘기지 않는다.

### 게이트가 꺼지는 출구는 하나여야 한다

`run_hook` 에 조용한 `return 0` 이 네 개 있었다. DB 를 못 읽는 경우를 막으면
`stages.json` 손상이 남았고, 그걸 막으면 head 없음이 남았다. 라운드마다 새 출구가
발견됐다 — **출구가 여러 개인 구조에서는 "다음 출구" 가 항상 남는다.**

`inactive(why, fix)` 하나로 모았다. 판정은 열어 주고(세션을 벽돌로 만들지 않는다)
꺼진 사실은 반드시 말한다. 새 출구를 더할 때 알림이 딸려 온다.

### 공허한 설정은 예측하지 않고 보여준다

같은 형태가 진단에도 있었다. 설정이 강제를 무력화하는 모양을 하나씩 예측해 규칙을
더했다 — 빈 목록, 아무것도 안 맞는 정규식, 이름 바꾸기, 조건 배열 비우기. 그래도
계속 새어나갔다(리뷰가 네 가지를 더 찾았다). **예측은 끝이 없다.**

그래서 `status` 가 **결과를 숫자로** 보여준다.

```
강제 중: 보호 경로 7 · 승인 필요 6/6 · 종료 조건 4/7 · 승격 게이트 1/1 · 턴 종료 게이트 2/7 · 쓰기 규칙 7/7 · 언어 ko
```

조건 이름을 바꾸고 Compounding 의 게이트를 지우면 `게이트 있는 단계 4/7 → 3/7` 로
보인다. 전부 비우면 `쓰기 규칙 0 · 게이트 있는 단계 0/7` 이 된다. **어떤 방식으로
비웠는지는 알 필요가 없다.**

그리고 텍스트를 읽어 판단해야 하는 곳은 **탐침한다.** `bash_pattern` 이 너무 넓은지
정규식을 분석하는 대신 `ls`·`echo hi`·`git status` 를 넣어 보고 걸리는지 본다.
파싱이 아니라 실험이다.

### 검사기는 파이썬의 스코프 규칙을 재구현하지 않는다

`ctx_check` 는 대입·인자·루프 변수를 모아 스코프를 흉내냈다. 두 번 틀렸고 둘 다
리뷰가 찾았다 — 중첩 함수의 대입을 바깥 바인딩으로 셌고, 고친 뒤에는 comprehension
변수를 바깥 바인딩으로 셌다. **패턴이 같다: 내가 파이썬의 규칙을 재구현하고 있었고,
규칙은 내 예상보다 많다.**

표준 라이브러리의 `symtable` 은 컴파일러가 쓰는 그 분석기다. 중첩 함수,
comprehension, `global`/`nonlocal`, walrus 를 전부 정확히 안다. 손계산 74줄을
지우고 그것으로 물어본다.

### 재연결은 상태 전이다

`loop adopt` 는 `create_loop`(`INSERT OR IGNORE`)에 회차 +1 을 얹은 것이었고,
세 가지가 어긋났다 — 없는 ID 를 adopt 하면 첫 상태가 회차 2, 연속 adopt 하면
경계 없이 회차만 올라 측정 창이 섞이고, 닫힌 작업을 되살려도 `closed_at` 이 남아
tidy 가 닫힌 것으로 봤다.

뿌리는 하나다. **`INSERT OR IGNORE` 가 "만들기"와 "이어받기"를 뭉갰고, `cycle` 이
접두사 구분자와 측정 창 번호를 겸했다.** 존재 여부를 명시적으로 갈라, 이어받을 때는
회차 경계(`cycle_close`)를 남기고 `closed_at` 을 지운다.

### 자기 잠금은 협상 대상이 아니다 (바닥값)

적대적 리뷰가 하네스의 자기 잠금을 **일곱 가지 모양으로** 열었다.

| 설정 | 결과 |
| --- | --- |
| `protected_paths: []` 또는 `null` | 엔진·DB 쓰기 통과 |
| `write_rules: []` | 모든 쓰기 규칙 소멸 |
| `bash.readers` 에 `rm` 추가 | `rm 엔진` 통과 |
| `bash.mutator_pattern: "(?!)"` | 문법은 맞고 아무것도 안 맞음 → 부모 디렉터리 보호 소멸 |
| `protected` 규칙에 `grant_opens: true` | 예외로 열림 |

뿌리는 하나다. **자기 잠금이 `stages.json` 에 있었고, 그 파일은 `context` 클래스라
여러 단계에서 모델이 쓸 수 있다.** 엔진을 쓸 수 있으면 모든 게이트가 끝난다.
0.30.0 엔진에서도 뚫렸으므로 어휘화가 만든 결함은 아니다 — 다만 표면을 넓혔다.
전에는 경로 목록만 비울 수 있었고 이제 규칙 자체를 지울 수 있다.

그래서 바닥값(`SELF_LOCK`)을 코드에 두고 **설정은 여기에 더할 수만 있다.**
보호 경로는 `바닥값 ∪ 설정` 이고, 바닥값에 대해서는 `grant` 도, `grant_opens` 도,
`mutator_pattern` 판정도 보지 않는다. `readers` 로 위장하는 것도 막는다 —
변경 명령 이름(`rm`·`mv`·`dd`·`find` …)은 읽기로 선언될 수 없다.

**"규칙이 틀렸으면 `stages.json` 을 고쳐라"는 그대로다.** 단 하나, 잠금을 푸는
방향으로는 고칠 수 없다. 근거 문서가 이미 "이 차단은 `allow` 로도 열리지 않는다"고
못박은 그 예외를 설정에도 적용한 것이다. `stages.json` 자체는 바닥값이 아니다 —
사람이 고쳐야 하는 문서이기 때문이다.

경계를 하나 지켰다. **읽기는 계속 통과한다.** `cat`·`grep` 으로 DB를 읽는 것까지
막으면 과잉 차단이고, 과잉 차단은 마찰이 되고 마찰은 게이트를 끄게 만든다. 처음
고칠 때 읽기까지 막았고, 기존 테스트가 그것을 잡았다.

### 재연결은 회차를 올린다

같은 리뷰가 찾은 것. 닫힌 작업을 `loop adopt` 로 재연결하면 접두사가 그대로여서
**1회차의 계획서가 이번 회차의 `plan_file` 을 채웠고**, 스킵까지 통과했다.
0.31.1 에서 `skip` 을 `criterion_met` 으로 바꾼 것(옳은 수정이었다)이 파일 판정과
만나 생긴 구멍이다. 재연결은 "1단계부터 다시"이므로 새 회차가 정직한 표현이다.
앞단 해시는 그대로라 과거 산출물은 여전히 `grep` 으로 모인다.

### 조건의 이름과 판정은 묶여 있다

어휘화는 판정 방식을 설정으로 내렸다. 그러면 **이름과 판정이 어긋날 수 있다.**
적대적 리뷰가 셋을 실증했고 전부 조용했다.

| 바꾼 것 | 결과 |
| --- | --- |
| `promotion_decided` → `file` | 미결 승격이 남아도 회차가 닫힌다 (복리 장치의 핵심 게이트) |
| `plan_approved` → `file` + `write_glob: ["**"]` | 접두사만 맞으면 **아무 파일이 사람의 승인**이 된다 |
| `plan_file` → `no_pending_promotions` | 산출물 없이 통과한다 |

엔진에 이름을 다시 박아 금지하지는 않았다 — 그건 어휘화를 되돌리는 것이다. 대신
**기본값(`defaults.json`)과 대조해 달라진 것을 말한다.** 사용자가 새로 만든 조건은
기본값에 없으므로 아무것도 말하지 않는다(오진 없음). 금지가 아니라 통보다 —
"의도한 것이면 그대로 두어라"라고 적는다.

진단이 닿는 자리도 넓혔다. 예전에는 활성 작업이 없으면 세션 시작이 **조용히**
빠져나갔다. 설치 직후나 DB를 지운 직후가 설정이 어긋났는지 가장 중요한 시점이다.
`PreToolUse` 마다 알리는 것은 일부러 넣지 않았다 — 도구 호출마다 같은 경고가 붙으면
그건 소음이고, 소음은 읽히지 않는다.

### 어휘화가 만든 새 실패 방식: 오타

규칙이 코드에 있을 때는 오타가 나면 파이썬이 죽었다. 설정으로 옮기면 오타가 **조용해진다.**
직접 돌려 확인한 것들이다.

| 오타 | 조용한 결과 |
| --- | --- |
| `satisfied_by: "fille"` | 파일 검사가 말없이 꺼진다. 파일이 있어도 조건이 안 선다 |
| `satisfied_by: "file"` + `write_glob` 없음 | 어떤 파일도 그 조건을 채울 수 없다 |
| `panels: ["work_candidatez"]` | 아무것도 하지 않는다 |
| `exit_criteria: ["없는_이름"]` | 채울 방법이 없어 그 단계를 끝낼 수 없다 |

사용자는 자기가 설정한 것이 동작한다고 믿는다. 그래서 `config_problems` 가 어휘 오류를
찾아 `status` 맨 위와 세션 시작 `systemMessage` 로 **말한다.** 막지는 않는다 — 설정이
조금 틀렸다고 세션을 벽돌로 만들면 그게 더 나쁘다. 비용은 훅 한 번의 0.1% 다.

`stages.json` 자체가 깨졌을 때는 다르다. **템플릿으로 갈아치우지 않는다** — 사용자가
덜어낸 규칙이 말없이 되살아나고, 그 사람은 이유 모를 차단만 보게 된다. 없는 것(설치 전)과
깨진 것은 다르다. CLI 는 `exit 1` 로 크게 실패하고, 훅은 차단하지 않되 세션 시작에
**하네스가 비활성이라는 사실과 되돌리는 방법**을 알린다. 조용히 꺼지는 것이 최악이다.

한 가지 함께 고쳤다. `skip` 이 `has_evidence` 만 봐서, 계획 파일이 디스크에 있는데도
"계획 파일을 남겨야 한다"고 거부했다 — 이미 한 일을 하라는 말이고 빠져나갈 길이 없었다.
0.30.0 에서 파일 판정을 넣을 때 이 경로를 맞추지 않은 탓이다. 이제 `advance` 와 같은
판정을 쓴다. **게이트를 여는 판정과 건너뛰는 판정이 다르면 그 차이가 곧 함정이다.**

## 어느 층이 강제하나 (훅이 없으면 무엇이 남는가)

이 하네스는 Claude Code 훅으로 시작했다. 그러면 "다른 도구에서도 쓸 수 있나"라는 질문이
따라온다. 조사해 보니 **훅 층만 보고 판단하면 틀린다.**

정면으로 도전한 사례들은 층을 내려간다.
[Agent Control Plane](https://agenticcontrolplane.com/integrations/codex) 은 Codex 훅이 셸만
가로챈다는 것을 인정하고 파일 조작을 MCP 커넥터로 흘려보낸다.
[Cupcake](https://cupcake.eqtylab.io/reference/harnesses/opencode/) 은 정책 엔진 하나에
도구별 어댑터를 붙인다.
[NVIDIA OpenShell](https://www.vietanh.dev/blog/2026-03-17-nvidia-openshell-agent-sandboxes) 은
훅을 아예 쓰지 않고 컨테이너와 eBPF/seccomp 로 커널이 강제하게 한다 — 에이전트가 프롬프트
인젝션으로 오염돼도 자기 가드레일을 끄지 못한다.

그래서 이 하네스의 게이트를 층으로 다시 갈랐다.

| 게이트 | 강제하는 층 | 훅이 없어도 되나 |
| --- | --- | --- |
| 단계 진행 (`advance` 거부) | CLI | 된다 — 어느 도구가 실행해도 거부한다 |
| 완료 조건·의도 기록 | CLI | 된다 |
| 계획 파일·회고 파일 존재 | 파일시스템 | 된다 — 관측 없이 디스크를 본다 |
| 검증 통과 (`verify`) | CLI 가 직접 실행 | 된다 — 종료 코드로 판정한다 |
| 승격 결정 | 이벤트 집계 | 된다 |
| 사람의 계획 승인 | CLI | 된다 (다이얼로그는 Claude 에서만) |
| 폴더·파일명 규칙 (쓰기 차단) | PreToolUse | **안 된다** |
| 하네스 자기 잠금 | PreToolUse | **안 된다** |
| 말머리, 턴 이어붙임 | Stop | **안 된다** |

즉 절차 강제와 증거 판정은 CLI·파일시스템에 있고, **즉시 차단과 말머리만 Claude 전용**이다.
"불가능에 가깝다"가 아니라 "층을 내려가면 즉시성을 잃는다"가 맞는 말이다. 쓰기 차단을 더
내려보낼 수는 있다 — git pre-commit 이나 OS 샌드박스 — 대신 차단 시점이 쓰기에서 커밋으로,
또는 별도 인프라로 옮겨간다. 그 값을 치를 이유가 생기기 전까지는 내려보내지 않는다.

`AGENTS.md` 에 절차 안내를 한 번 붙이는 것은 그 값이 0이라서 넣었다. `@import` 는 쓰지 않는다
— 그건 Claude Code 기능이고, 이 파일을 읽는 다른 도구들은 그냥 마크다운으로 읽는다.

## 증거는 관측이 아니라 사실이어야 한다

두 가지를 고쳤고, 둘 다 실제로 새고 있었다.

**첫째, 파일 존재는 관측을 기다릴 필요가 없다.** `plan_file` 과 `retro_file` 은 PostToolUse 로
쓰기를 관측해서만 적립됐다. 훅이 없는 세션·다른 도구·사람이 직접 쓴 파일에서는 조건이 영원히
채워지지 않고, 남는 길은 `skip` 뿐이다. 그건 "했다"가 아니라 "건너뛰었다"로 기록된다.
**정직한 기록을 남길 방법이 없으면 사람은 부정직한 기록을 남긴다.** 그래서 관측된 증거가
없으면 디스크를 본다. 단, 이번 회차 접두사(`<작업해시>-<회차>-`)를 **요구한다** — 지난 회차의
계획서가 이번 회차의 게이트를 열면 그건 사람 없이 게이트가 열리는 것이다. 누적 인덱스도
같은 이유로 제외된다.

**둘째, 테스트를 돌린 것과 통과한 것은 다른 사실이다.** `verification_evidence` 는 명령
**문자열만** 봤다. 그래서 `pytest` 를 돌려 3개가 깨져도 증거가 적립되고 Verification 게이트가
열렸다. 실제로 그렇게 통과하는 것을 확인했다. 이제 실패한 도구 호출은 증거로 세지 않고,
훅이 없는 자리에는 `harness verify -- <명령>` 이 있다 — 하네스가 직접 돌리고 종료 코드로
판정한다. "검증했습니다"라는 자기 보고는 받지 않는다. 받는 순간 이 게이트는 장식이 된다.
`verify` 가 돌릴 수 있는 명령은 검증 패턴으로 제한하고 셸 메타문자를 거부한다 — 제한하지
않으면 이것이 PreToolUse 를 우회하는 셸이 된다.

- [State of AI Agent Memory 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026) — 배경

도구 간 이식성은 아래를 조사했다.

- [Agent Control Plane](https://agenticcontrolplane.com/integrations/codex) — 훅이 못 보는
  도구는 MCP 로 흘려보낸다
- [Cupcake](https://cupcake.eqtylab.io/reference/harnesses/opencode/) — 정책 엔진 하나 +
  도구별 어댑터 (Claude Code·Cursor·OpenCode·Factory AI)
- [NVIDIA OpenShell](https://www.vietanh.dev/blog/2026-03-17-nvidia-openshell-agent-sandboxes)
  — 훅 대신 커널이 강제한다. 에이전트를 고치지 않고 감싼다
- [Context Files 가 지배적이다](https://arxiv.org/abs/2602.14690) — 대부분의 저장소는 컨텍스트
  파일이 유일한 수단이다. Skills·Subagents 를 쓰는 곳은 드물다
- [ZORO: active rules](https://arxiv.org/abs/2604.15625) — 규칙 파일은 수동적이다. 단계마다
  걸고 준수의 증명을 요구해야 한다 (이 하네스의 종료 조건과 같은 결론)

## 막혔을 때

```sh
.claude/harness/bin/harness status                              # 현재 단계·종료 조건·증거
.claude/harness/bin/harness advance                             # 다음 단계 (조건 미충족이면 거부)
.claude/harness/bin/harness advance --done                      # (Compounding) 작업 종료 → Selection
.claude/harness/bin/harness advance --cycle                     # (Compounding) 다음 회차 → Scaffolding
.claude/harness/bin/harness skip <stage|+N|until:<stage>> --reason "..."   # 사용자 승인 필요
.claude/harness/bin/harness allow "docs/spec/003-x.md" --reason "..."      # 쓰기 예외, 사용자 승인 필요
.claude/harness/bin/harness approve-plan .dev/plan/<해시>-x.md   # 계획 승인 기록
.claude/harness/bin/harness loop                                 # 현재 작업 해시·브랜치
.claude/harness/bin/harness loop new --intent "..."              # 작업을 닫고 새로 시작
.claude/harness/bin/harness loop adopt <해시> --reason "..."      # 기존 해시로 재연결
```

차단은 하네스가 틀렸다는 신호일 수도 있다. 규칙 자체가 작업을 방해한다면 그것을 Compounding에서
논의하라 — `stages.json` 이 규칙의 단일 출처이고 수정 가능하다.
